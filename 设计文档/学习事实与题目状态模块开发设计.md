# 学习事实与题目状态模块开发设计

> 状态：跨模块契约已确定，详细表结构待补充。

本文档定义正式学习事件、当前题目、作答记录和学习进度的权威状态管理。

## 1. 一句话定义

```text
学习事实模块是学生真实学习行为的事实账本，
负责保存和查询当前题、查看答案、正式提交、判题结果和状态版本，
但不负责判题算法、知识追踪计算、教学规划或回复生成。
```

## 2. 数据所有权

学习事实模块拥有以下持久化数据：

```text
CurrentQuestionState
AnswerRevealFact
AnswerSubmission
GradingResult
AnswerEvidence
EvidenceEligibility
FormalLearningEvent
OutboxEvent
```

其他模块的职责：

```text
判题与作答证据模块：生成 Submission、Grading、Evidence 和 Eligibility。
学习事实模块：在一个事务中保存这些正式事实，并提供查询和恢复。
KT 模块：只消费已经合格的 FormalAnswerRecorded，不修改原始事实。
TeachingTrace：记录引用和处理过程，不代替事实账本。
Memory / RAG / LLM：只读正式事实，不能覆盖事实。
```

判题模块通过 `LearningFactStore` 接口写入，不能直接拥有另一套作答数据库。

第一阶段的正式 Adapter 使用 SQLite，适配个人或少量用户的单机部署。业务代码只依赖 `LearningFactStore`，未来出现真实多用户并发需求时再增加 PostgreSQL Adapter。

## 3. 统一名称

命令、事实和领域事件必须分开命名。

| 动作 | 命令 | 保存的事实 | 领域事件 |
|---|---|---|---|
| 提交答案 | `SubmitAnswerCommand` | `AnswerSubmission` | `formal_answer_recorded` |
| 查看答案 | `RevealAnswerCommand` | `AnswerRevealFact` | `answer_revealed` |
| 请求下一题 | `RequestNextQuestionCommand` | `NextQuestionRequestFact` | `next_question_requested` |
| 换题 | `ChangeQuestionCommand` | `QuestionChangeFact` | `question_changed` |

兼容规则：

```text
answer_submitted：旧 /api/events 的兼容事件名。
answer_submission：旧 Runtime capability 名称。
新模块不得继续把这两个名称当作新的领域事件名。
```

## 4. 正式提交事务

正式提交按以下顺序处理：

```text
SubmitAnswerCommand
  → 判题与证据模块生成正式结果
  → LearningFactStore 原子保存全部事实
  → eligible_for_kt=true 时，在同一事务写 formal_answer_recorded outbox
  → 数据库提交成功
  → 存在 formal_answer_recorded 时，同步尝试让 KT 消费事件
  → KT 失败时由 outbox 后台重试
```

提交接口最多同步等待 KT 1500 ms：

```text
1500 ms 内成功：kt_status=succeeded，并返回 TeachingState 引用。
超过 1500 ms：kt_status=pending，后台继续处理。
明确失败：kt_status=failed，保留 outbox 等待重试。
不符合准入条件：kt_status=skipped。
```

事实保存不依赖 KT 成功。

```text
KT 成功：返回最新 TeachingState 引用。
KT 跳过：返回明确的跳过原因。
KT 失败：作答和判题仍然有效，记录为可重试状态。
```

## 5. KT 准入权威

`EvidenceEligibility.eligible_for_kt` 是作答能否进入 KT 的唯一业务结论。

判题与证据模块负责综合判断：

```text
是否正式提交。
是否完成确定性判题。
提交前是否查看答案。
题目和知识点映射是否满足要求。
```

`submission_id` 是否已经被 KT 消费由事件分发和 KT 消费幂等负责，不改变原始 `eligible_for_kt`。

KT 模块不得重新根据 `answer_viewed`、原始 payload 或聊天内容计算另一份准入结果。

KT 只消费已经发布的 `formal_answer_recorded` 事件。

同一个 `(student_id, question_id, question_state_version)` 中，只有第一次满足条件的独立正式作答可以生成 `formal_answer_recorded`。后续尝试继续保存和判题，但不重复进入 KT；题目状态版本变化后重新计算。

## 6. 状态版本

不同状态使用不同版本，禁止全部叫 `progress_version`：

```text
question_state_version：当前题状态版本，用于防止旧页面提交。
learning_fact_version：事实账本版本，新增正式事实时递增。
kt_state_version：KT / TeachingState 版本，仅 KT 成功更新时递增。
```

因此，提交前已经查看答案的作答：

```text
learning_fact_version 递增。
kt_state_version 不变。
```

## 7. 不变量

```text
同一个 submission_id 只能对应一份请求内容。
网络重放不产生新的学习事实。
查看答案不等于答错或掌握。
无法判题不等于回答错误。
GradingResult 不得被 KT、Memory、RAG 或 LLM 覆盖。
TeachingState 不得反向修改历史判题结果。
Trace 丢失不能导致正式学习事实丢失。
KT 失败不能回滚已经成功保存的作答和判题事实。
```

## 8. 学生数据删除

删除单条长期记忆由记忆系统负责；删除整个学生时，学习事实模块负责协调删除：

```text
学习事实和当前题状态。
对话与记忆原料。
正式长期记忆对应的 HMS student bank。
待处理 outbox、记忆提炼和 HMS 同步任务。
TeachingState 和可识别学生的 Trace 内容。
```

允许保留不含学生正文、答案和可识别 ID 的聚合运行指标。删除操作必须幂等并记录不含敏感正文的最小审计结果。
