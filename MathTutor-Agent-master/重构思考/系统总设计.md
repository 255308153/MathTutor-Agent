# 系统总设计

这份文档记录 MathTutor Agent 的整体产品和系统结构构想。

它和 `思考链路.md` 的区别是：

```text
系统总设计：页面长什么样、模块怎么分、状态怎么同步。
思考链路：一次事件进来后，系统怎么路由、调用工具、记录 trace。
```

## 产品使用构想

页面的主心智模型是“当前题目 + 侧边 Agent 辅导”，不是纯聊天页面。

建议分成三个核心模块：

```text
1. 当前题目区
2. 左侧 Agent 对话模块
3. 下一题按钮 / 推荐说明
```

## 当前题目区

当前题目区负责展示学生现在正在做的题。

这里应该有：

```text
题干
答案输入
提交答案按钮
当前题状态
可选的简短推荐说明
```

提交答案只做状态保存：

```text
学生写答案
-> 点击提交答案
-> 保存作答记录
-> 可选确定性判题
-> 更新当前题状态
-> 不触发 agent 对话
-> 不自动推荐下一题
```

也就是说，提交答案不是一次 agent 对话，它只是把“学生做过这道题”这件事保存下来。

## Agent 对话模块

左侧侧边栏是 Agent 对话模块。

它应该支持：

```text
新增对话
选择历史对话继续
围绕当前题提问
询问为什么推荐这道题
询问当前题怎么做
询问错因
询问下一步学习建议
```

Agent 对话模块会读取当前页面状态：

```text
当前题
当前题作答状态
学生历史作答
推荐题来源
系统内部学生画像/记忆
必要时的 RAG 资料
必要时的 KT/DGEKT 诊断
```

但 Agent 不应该每次对话都调用所有工具。

它只在用户问题需要时调用：

```text
问当前题怎么做 -> task_state + 可选 RAG + 可选 Memory
问为什么推荐这题 -> recommendation_evidence + 可选 KT + 可选 Memory
问下一步做什么 -> KT + Recommender
问泛化概念 -> 可选 RAG
闲聊 -> 不调用重工具
```

这里的 Memory 是内部系统能力，不是用户可直接操作的功能。

用户不能手动新增、删除、禁用或编辑记忆。

系统只在后台根据学习行为和对话证据维护学生画像，用来辅助个性化讲解和推荐。

## 下一题按钮

下一题按钮是一个明确的系统动作，不是普通聊天。

点击后：

```text
读取当前学习状态
按需调用 KT/DGEKT
读取历史做题记录
读取题库候选
可选读取 Memory
调用 Recommender 选下一题
更新当前题
保存 pending/current question 状态
生成简短推荐说明
```

这个按钮应该自动把页面跳到下一题。

同时在题目区的小位置展示一句简短说明：

```text
推荐原因：你刚才在分数通分上出错，这题会继续练同一知识点，但难度略低。
```

如果用户在 Agent 对话里追问“为什么选这道题”，Agent 再读取更完整的推荐证据，生成更详细解释。

## 状态同步原则

当前题目区、下一题按钮、Agent 对话模块共享同一份学习状态。

```text
提交答案 -> 更新作答状态
点击下一题 -> 更新 current_question / pending_question
Agent 对话 -> 读取当前状态，并在必要时由系统后台更新内部画像
历史对话 -> 可以继续读取当时或当前的题目上下文
```

这里要区分两类状态：

```text
学习事实状态：题目、答案、判题结果、进度、当前题
对话状态：某个 Agent 对话里问过什么、解释过什么
内部画像状态：系统从长期学习行为中提取的偏好、错因、有效策略
```

学习事实状态是全局共享的。

对话状态属于某个 conversation，但可以引用当前学习事实。

内部画像状态由系统维护，不提供给用户直接操作。

## 设计边界

```text
题目区负责做题和保存作答状态。
下一题按钮负责推进当前题。
Agent 侧边栏负责解释、答疑、复盘和学习建议。
提交答案不触发 Agent。
Agent 需要基于当前题和历史状态回答问题。
记忆系统是内部能力，用户不直接操作。
```

一句话总结：

```text
题目是主界面，Agent 是侧边辅导层，下一题按钮是明确的学习推进动作。
```
