# 完整流程预演

这份文档记录 MathTutor Agent 目标态的一次完整使用流程。

它只记录已经讨论确定的规则。后续继续预演时，按步骤往下补。

---

## 前置：全局状态分层

系统里要区分几类状态。

```text
学习事实状态：
  当前题、作答记录、判题结果、查看答案记录、KT 状态、推荐历史、换题反馈。

短期对话记忆：
  属于某一个 conversation，只记录这个对话框最近聊了什么、AI 讲过什么、当前指代关系。

长期学生画像：
  属于 student，跨对话框共享，记录稳定偏好、反复错因、有效讲法、学习目标等。

TeachingState：
  由判题事实和 KT 输出编译成的只读状态快照。
```

核心规则：

```text
一个学生 = 一份长期画像。
一个对话框 = 一份短期现场。
多个对话框共享长期画像、学习事实、KT、推荐历史、换题反馈。
多个对话框不共享彼此的短期聊天记录。
其他对话框的内容只有经过后台提纯，变成长期记忆后，才可以被新对话读取。
```

## 0. 新学生首次进入平台

场景：

```text
学生第一次进入平台。
系统没有可靠历史记录。
KT 为空或 unknown。
长期画像为空。
```

这一步只有一个入口。

先让学生选择已经接触过的知识点，再选择要进一步学习的目标知识点，最后选择当前学习状态。

### 0.1 唯一入口

新学生首次进入时，先做学习背景选择：

```text
我之前接触过哪些知识点？
```

学生可以勾选多个已经接触过的知识点。

例如：
```text
我接触过：
  加法原理
  乘法原理
  长方形面积
  简单分数计算
```

这里的“接触过”只表示：

```text
学生接触过这个知识点。
```

它不表示：

```text
学生已经掌握这个知识点。
```

系统记录为：

```text
prior_exposure:
  concept_id
  status = self_reported_learned
  confidence = low
```

注意：

```text
prior_exposure 不会自动创建 learning_state_by_concept。
prior_exposure 不会让这个知识点自动进入“继续学习”列表。
只有学生选择某个知识点作为目标，并真正开始学习时，
才创建 learning_state_by_concept，
这个知识点才进入“继续学习”列表。
```

然后学生选择要进一步学习的目标知识点：

```text
我接下来想学习 / 深入练习哪个知识点？
```

目标知识点来源可以来自完整 XES3G5M 的知识点路径。

例如：

```text
拓展思维 / 计数模块 / 加乘原理
几何 / 长方形周长
几何 / 长方形面积
方程
分数
```

选择目标知识点也不是掌握证据。

```text
学生选择分数加法 = 学生想进一步学习分数加法。
不等于学生已经掌握分数加法。
```

最后选择当前状态：

```text
初次学习
复习
正在练习
```

这三个选择只表示学习意图和学习背景，不是掌握证据。

不能写成：

```text
勾选接触过 = 学生掌握这个知识点。
选择某目标知识点 = 学生掌握这个知识点。
选择初次学习 = 学生不会。
选择复习 = 学生会。
选择正在练习 = 学生已掌握。
```

完成这个首次选择后，首页才可以开始分成两块：

```text
继续学习
探索新知识点
```

其中：

```text
有 learning_state_by_concept = 出现在继续学习列表。
没有 learning_state_by_concept = 出现在探索新知识点列表。
```

注意：

```text
继续学习 ≠ 已掌握。
继续学习只表示学生已经开始过这个知识点。
继续学习不是只有一个知识点。
学生可以同时在多个知识点上有学习进度。
```

### 0.2 如果选择“初次学习”

系统不需要先测很多题。

因为学生表达的是：

```text
我想从头学。
```

流程：

```text
记录 onboarding_preference
-> 记录 prior_exposure
-> 初始化目标知识点 KT = unknown / low confidence
-> 已接触过的相关知识点只记录 exposure，不写 mastery
-> Recommender 从该知识点下选择低难度 / 入门题
-> current_question = 入门题
-> 写 recommendation_history
-> 写 TeachingTrace
-> 页面进入第一题
```

推荐规则：

```text
优先选择：
  知识路径更基础的题
  题干短的题
  有答案和解析的题
  图片依赖少的题
  历史正确率较高的题
```

这时第一题的目的不是快速判断学生水平，而是：

```text
低门槛开始学习。
```

### 0.3 如果选择“复习”

系统需要先了解一下学生现在还记得多少。

流程：

```text
记录 onboarding_preference
-> 记录 prior_exposure
-> 初始化目标知识点 KT = unknown / low confidence
-> 已接触过的相关知识点只记录 exposure，不写 mastery
-> 进入短诊断
-> 推荐 2-3 道该知识点下的代表题
-> 学生独立提交
-> 根据 grading_result 更新 KT
-> 再进入正常练习
```

题目选择：

```text
基础题 1 道
中等题 1 道
必要时再补 1 道
```

如果学生勾选了多个已接触过的相关知识点，可以少量加入轻融合题候选。

但注意：

```text
轻融合题只是候选。
初期权重不能太高。
不要一上来推复杂综合题。
```

如果答得好：

```text
后续可以推荐中等 / 稍高难度题。
```

如果答得不好：

```text
降到基础题，并多给讲解。
```

### 0.4 如果选择“正在练习”

系统也需要先了解当前水平，但可以比“复习”更接近练习状态。

流程：

```text
记录 onboarding_preference
-> 记录 prior_exposure
-> 初始化目标知识点 KT = unknown / low confidence
-> 已接触过的相关知识点只记录 exposure，不写 mastery
-> 进入短诊断
-> 推荐 2-3 道该知识点下的代表题
-> 学生独立提交
-> 根据 grading_result 更新 KT
-> 再继续推荐相近题
```

题目选择：

```text
中等题 1 道
相近题 1 道
必要时根据对错补一题
```

如果学生勾选了多个已接触过的相关知识点，可以加入少量融合题候选，用来观察当前综合运用能力。

但融合题推荐仍然要保守：

```text
有正式作答证据前，只能轻量尝试。
不能因为学生勾选“接触过”，就直接大量推荐融合题。
```

如果连续正确：

```text
可以逐步提高难度。
```

如果连续错误：

```text
回到基础题或概念复习。
```

### 0.5 三种状态的区别

```text
初次学习：
  直接从低难度 / 入门题开始。
  不急着判断掌握度。

复习：
  先做 2-3 道短诊断题。
  了解学生还记得多少。

正在练习：
  先做 2-3 道代表题。
  快速定位当前练习水平。
```

已接触过的相关知识点：

```text
只表示 prior_exposure。
用于判断是否可以尝试轻融合题。
不直接改变 mastery。
```

### 0.6 KT 更新规则

不管是哪种入口，KT 都只由正式作答更新。

正式作答必须满足：

```text
未看答案
点击提交答案
系统判题
生成 grading_result
```

然后才更新：

```text
KT
mastery
TeachingState
```

这些不更新 KT：

```text
选择已接触过的知识点
选择目标知识点
选择初次学习 / 复习 / 正在练习
看答案
跳过
换题
问 Agent
```

### 0.7 写入和不写入

这一步可以写入：

```text
onboarding_preference
selected_knowledge_point
prior_exposure
learning_entry_mode
current_question
recommendation_history
TeachingTrace
```

`onboarding_preference` 可以记录：

```text
student_id
selected_knowledge_point
prior_exposure_concepts
learning_entry_mode：first_learn / review / practicing
source：onboarding
created_at
```

这一步不写入：

```text
不因为选择知识点就更新 KT。
不因为勾选“接触过”就写学生掌握。
不因为选择“初次学习”就写学生不会。
不因为选择“复习”就写学生会。
不因为选择“正在练习”就写学生掌握。
不生成长期画像结论。
不自动展开所有知识点 mastery。
```

### 0.8 关于完整 XES3G5M 数据

完整 XES3G5M 可以提供：

```text
题目文本
标准答案
解析
题型
知识点路径
历史作答序列
```

但当前没有直接看到：

```text
年级
教材版本
章节
显式难度
```

所以新学生首次进入时，不能直接按年级判断掌握度。

题目难度可以先用规则估计：

```text
知识路径深浅
题干长度
题型
是否依赖图片
历史正确率
```

这些只用于推荐，不直接写成 KT 结论。

核心规则：

```text
新学生只有一个入口：
先选择已接触过的知识点，
再选择要进一步学习的目标知识点，
最后选择学习状态。

已接触过 = prior_exposure。
已接触过不等于掌握。
已接触过不会自动进入继续学习列表。

初次学习：
  直接从低难度入门题开始。

复习 / 正在练习：
  先做 2-3 道题了解水平。

如果学生勾选了多个相关知识点：
  可以把轻融合题作为候选。
  但融合题权重不能太高。
  只有正式作答证据变多后，融合题权重才逐步提高。

所有入口下，KT 初始仍是 unknown / 低可信度。
只有未看答案前的正式提交，才更新 KT / mastery。
```

## 1. 当前题展示

场景：

```text
学生打开页面。
页面展示 current_question。
```

已确认规则：

```text
只读展示 current_question。
不记录“学生看到了这道题”。
不触发 Agent。
不调用 RAG。
不调用 Memory。
不重新计算 KT。
不推荐下一题。
```

这一步只是页面渲染，不是学习事件。

## 2. 显示答案

场景：

```text
学生点击“显示答案”。
页面展开标准答案或参考解析。
```

流程：

```text
读取 current_question
-> 展示 standard_answer / explanation
-> 检查当前题是否已有 answer_submitted
-> 记录 answer_revealed
-> 不触发 Agent
-> 不调用 RAG / Memory
-> 不更新 KT
-> 不改变 mastery
-> 不推荐下一题
```

`answer_revealed` 必须记录查看答案发生在提交前还是提交后：

```text
question_id
student_id
session_id
answer_submitted_before_reveal：true / false
reveal_timing：before_submit / after_submit
created_at
```

解释：

```text
answer_revealed 只证明学生看过答案。
它不证明学生会了。
它不证明学生不会。
它不等于答对或答错。
```

如果是提交前查看答案：

```text
reveal_timing = before_submit
```

后续推荐可以更保守。

如果是提交后查看答案：

```text
reveal_timing = after_submit
```

这只是学生在看解析，不影响下一题推荐保守程度。

后续推荐或解释可以参考 `answer_revealed`，但不能直接用它改掌握度。

## 3. 提交答案

场景：

```text
学生在答案框输入答案，并点击提交。
```

流程：

```text
读取 current_question
-> 检查提交前是否已有 answer_revealed 且 reveal_timing = before_submit
-> 保存 answer_submitted
-> 确定性判题
-> 显示正确 / 错误
-> 更新当前题作答状态
-> 如果提交前没有查看答案，更新 KT
-> 如果提交前已经查看答案，不更新 KT，只标记 submitted_after_reveal
-> 编译 TeachingState
-> 如果是未看答案前的正式提交，触发第 18 步 phase 检查
-> 记录 TeachingTrace
-> 返回简短状态反馈
```

页面可以立刻显示：

```text
本题正确。
```

或：

```text
本题错误。
```

但这一步不做：

```text
不自动讲解。
不自动推荐下一题。
不调用 RAG。
不读取 Memory。
不写长期记忆。
不进入 Agent 对话。
```

这一步是学习事实更新，不是教学回复。

注意：

```text
提交答案要区分两种情况：

提交前没有查看答案：
  这是独立作答。
  可以更新 KT。
  可以影响 mastery。

提交前已经查看答案：
  这是看答案后的提交。
  可以判题和记录。
  但不更新 KT。
  不改变 mastery。
  不推进 phase。

提交后才查看答案：
  这是看解析。
  不反过来影响刚才的 KT 更新。
  不让后续推荐变保守。
```

## 4. 学生问“我为什么错？”

场景：

```text
学生刚提交答案，系统已判定错误。
学生在 Agent 侧边栏问：我为什么错？
```

这一步进入 Agent 对话。

读取顺序：

```text
必读：
  current_question
  刚才的 answer_submitted
  grading_result
  最新 TeachingState
  当前 conversation 的短期对话记忆

按需读取：
  RAG 当前题解析 / 当前知识点 / 错因模式
  学生级长期画像
```

短期对话记忆每次 Agent 对话都要读：

```text
用于承接当前对话里刚才讲到哪里。
用于理解“这里”“那一步”“刚才那个”。
用于避免重复讲同一段。
```

长期学生画像按需读：

```text
学生过去在同一知识点反复错过。
学生有稳定讲法偏好。
学生之前对某种解释方式有正反馈。
当前问题需要个性化解释。
```

边界：

```text
Memory 只影响讲法，不决定错因。
RAG 只提供解释证据，不改写判题或 KT。
TeachingState 只读，不由回复流程改写。
```

错因规则：

```text
能从答案、步骤或明确规则直接确定错因，就记录确定错因。
不能确定，就记录 mistake_type = unknown。
不能把“常见错因”直接写成学生本次真实错因。
不主动追问学生补步骤。
```

回复策略：

```text
如果错因确定：
  直接解释错在哪里，并给正确方法。

如果错因不确定：
  说明当前证据不足，只能给可能原因和正确方法。
```

## 5. 交互记录与记忆

每次 Agent 回复都要保存完整交互。

```text
学生输入
AI 完整回复
本轮读取的事实
本轮使用的 RAG 引用
本轮使用的短期记忆和长期画像
是否产生推荐、换题或后续作答
```

记忆整理时要区分三类证据：

```text
学生证据：
  学生原话、正式作答、查看答案、换题反馈。

AI 行为：
  AI 完整回复、用过的提示、解释、引用和推荐。

结果证据：
  回复后的作答结果、换题行为、学生后续反馈。
```

长期记忆生成规则：

```text
学生偏好主要依据学生证据。
反复错因必须依据真实作答，不能依据 AI 对学生的描述。
AI 回复可以证明“系统讲过什么”，避免重复讲解。
有效教学策略必须同时有 AI 行为和后续结果证据。
不能只因为 AI 使用过某种讲法，就判定这种讲法有效。
```

后台提纯：

```text
主回复先结束。
完整交互写入主交互记录。
后台 LearningMemoryRefinery 异步判断是否沉淀长期记忆。
如果生成长期记忆，另存关联的 memory_update 记录。
```

## 6. Agent 问“下一步练什么？”

场景：

```text
学生在 Agent 侧边栏问：下一步练什么？
```

这只是一次问答，不是真正切换题目。

流程：

```text
识别意图：next_step_advice
-> 读取当前学习状态
-> 读取 current_question
-> 读取最近作答记录
-> 读取最新 TeachingState
-> 读取当前 conversation 的短期对话记忆
-> 按需读取学生级长期画像
-> 根据当前状态生成建议性回复
-> 保存学生输入 + AI 完整回复 + 使用证据
-> 记录 TeachingTrace
```

这一步不做：

```text
不更新 current_question。
不调用 Recommender 选择新题。
不跳转页面。
不自动推荐下一题。
不更新 KT。
不改变 mastery。
不写长期记忆。
```

回复可以是：

```text
从当前状态看，你下一步适合继续练这个知识点的相近题。
如果你准备好了，可以点击“下一题”按钮，系统会按这个方向切到下一题。
```

核心规则：

```text
Agent 里问“下一步练什么”只解释当前状态和建议方向。
它不推进学习进度，也不切换 current_question。
```

## 7. 点击“下一题”按钮

场景：

```text
学生已经完成当前题的一个结束动作。
页面上点击“下一题”按钮。
```

这才是真正推进学习状态、切换当前题的动作。

前置条件：

```text
当前题已有 answer_submitted。
或当前题已有 answer_revealed 且 reveal_timing = before_submit。
```

也就是说：

```text
提交过答案 -> 可以进入下一题。
提交前看过答案 -> 可以进入下一题。
既没提交，也没提交前看答案 -> 不允许进入下一题。
```

如果当前题既没提交，也没看答案：

```text
不切题。
提示：请先提交答案，或者查看答案后再进入下一题。
```

正常流程：

```text
点击下一题按钮
-> 检查当前题结束状态
-> 如果当前题是错的融合题且需要学生自选卡点，先进入第 20 步
-> 读取最新 TeachingState
-> 读取最近作答历史
-> 读取最近 10 条换题反馈
-> 读取题库候选摘要
-> 按需读取学生级长期画像
-> PracticePathPlanner 决定练习路径
-> Recommender 选择候选题
-> 第一道候选题成为新的 current_question
-> 保存 recommendation_history
-> 生成页面上的简短推荐说明
-> 页面跳转 / 刷新到下一题
-> 记录 TeachingTrace
```

当前题结束状态分三种：

```text
answer_submitted = true：
  可以进入下一题。
  如果提交前没有看答案，KT 已经在提交时更新。
  如果提交后查看了解析，不影响推荐保守程度。

answer_submitted = false 且 reveal_timing = before_submit：
  可以进入下一题。
  记录 skipped_after_reveal。
  推荐可以更保守。

answer_submitted = false 且 answer_revealed = false：
  不允许进入下一题。
```

特殊拦截：

```text
如果当前题是 mixed_concept，
且 grading_result = wrong，
且 answer_revealed = true，
且 reveal_timing = after_submit，
且还没有 mixed_error_self_diagnosis，
则不直接推荐下一题。
先进入第 20 步，让学生选择主要卡住的知识点。
```

这一步可以写入：

```text
current_question
recommendation_history
推荐原因
候选题池摘要
TeachingTrace
```

这一步不写入：

```text
不更新 mastery。
不更新 KT。
不写长期记忆。
不生成完整 Agent 对话回复。
```

原因：

```text
推荐本身不是作答证据。
只有学生后续对新题作答，才会再次更新 KT 和 TeachingState。
```

注意：

```text
如果是提交答案后点击下一题，KT 已经在提交答案时更新过。
如果是提交前看答案后点击下一题，本次点击不更新 KT，并且推荐可以更保守。
如果是提交后看解析再点击下一题，不触发保守推荐。
```

核心规则：

```text
下一题按钮负责推进学习状态。
它基于最新 TeachingState 和学习历史选题，更新 current_question，并让页面进入下一题。
```

## 8. 点击“换题”按钮

场景：

```text
页面当前题是 q_frac_014。
这题是系统通过“下一题”按钮推荐出来的。
学生看了题目后觉得不合适。
学生点击“换题”。
```

这一步不是普通 Agent 对话，也不是随机换题。

核心性质：

```text
换题是一次结构化推荐反馈。
它记录学生为什么不想做当前题。
它根据反馈重排或重选题目。
它刷新 current_question。
它影响推荐，不影响掌握度。
```

### 8.1 弹出反馈框

点击“换题”后，页面弹出反馈框。

可选原因：

```text
太简单
太难
不想练这个知识点
题型不喜欢
已经做过类似题
想先复习概念
其他：自由输入
```

学生必须选择一个原因，或者填写自由输入。

如果学生取消：

```text
不写反馈。
不换题。
不刷新 current_question。
```

### 8.2 记录 RecommendationFeedback

一旦学生提交反馈，先立即记录一条换题反馈。

记录内容：

```text
from_question_id：原来的 current_question
reason_type：太难 / 太简单 / 不想练这个知识点 / ...
reason_text：学生补充说明
student_id
session_id
conversation_id?  # 页面按钮触发可以为空；如果从 Agent 中触发则记录
created_at
```

这条记录保存到学习事实 / 推荐历史里。

注意：

```text
单次换题反馈不直接写入长期画像。
单次换题反馈不直接改变学生掌握度。
```

同时维护最近 10 条换题反馈：

```text
recommendation_feedback_history[-10:]
```

这 10 条用于后续推荐时参考，例如避免反复推荐学生刚刚拒绝过的类型。

### 8.3 根据反馈调整推荐方向

不同原因对应不同处理：

```text
太难：
  同知识点，降低难度。

太简单：
  同知识点，提高难度，或者换成综合题。

不想练这个知识点：
  从其他薄弱知识点里选。
  但不能写成“学生已经掌握当前知识点”。

题型不喜欢：
  降低当前题型的推荐权重。

已经做过类似题：
  提高近期重复惩罚，减少相似题。

想先复习概念：
  优先选概念复习 / 基础题。
  或页面提示“可以先看概念复习”。
  但不触发 Agent 自由聊天。

其他：
  先尽量解析学生的真实意图。
  解析不了，就保守换一道同知识点相近题。
```

这里的“调整推荐方向”，只是在影响下一道题怎么选。

它不代表：

```text
学生说太简单 = 学生已经掌握。
学生说太难 = 学生一定不会。
学生说不想练 = 这个知识点已经没问题。
```

### 8.4 Recommender 重排或重选

推荐模块读取：

```text
当前 TeachingState
原 current_question
最近作答历史
最近 10 条换题反馈
题库候选
本次 RecommendationFeedback
学生级长期画像（可选）
```

推荐模块输出：

```text
新的候选题池
新的 current_question
换题原因说明
```

优先规则：

```text
优先从原候选题池里重排。
如果原候选池没有合适题，再重新选题。
```

例如：

```text
原候选池：
q_frac_014
q_frac_018
q_frac_021

学生反馈 q_frac_014 太难。

系统优先在原候选池里找更基础的同知识点题。
如果没有，再从题库重新找。
```

### 8.5 刷新页面

选出新题后：

```text
current_question = 新题
页面刷新到新题
显示简短换题说明
```

页面说明只需要短，不需要像 Agent 一样长篇解释。

例子：

```text
已换成一道同知识点但更基础的题。
```

或者：

```text
已避开刚才的题型，换成另一道相近练习。
```

### 8.6 写记录

这一步写入：

```text
RecommendationFeedback
recommendation_feedback_history 最近 10 条
recommendation_history
current_question
TeachingTrace
```

TeachingTrace 至少记录：

```text
原推荐题
学生反馈
调整规则
新推荐题
是否来自同一候选池
前后难度
前后知识点
```

这样以后可以追溯：

```text
为什么 q_frac_014 被换掉？
为什么后来换成 q_frac_018？
这次换题是因为太难、太简单，还是题型不喜欢？
系统有没有连续推荐学生不喜欢的题型？
```

### 8.7 不允许做的事

点击“换题”不允许：

```text
不更新 KT。
不改变 mastery。
不把“太简单”写成学生已掌握。
不把“太难”写成学生不会。
不触发 Agent 自由对话。
不写长期记忆。
```

原因：

```text
换题反馈只是学生对推荐题目的即时感受。
它不是一次作答结果。
它不能直接证明学生掌握或没掌握。
```

### 8.8 长期画像怎么处理多次换题反馈

单次换题反馈不直接写长期画像。

长期画像只能在后台根据多次反馈提炼趋势。

例如：

```text
学生最近多次反馈题目太难。
学生最近多次拒绝某类题型。
学生对某知识点的题目难度感受不稳定。
```

如果同一题 / 同一知识点先反馈“太难”，后来又反馈“太简单”：

```text
原始 RecommendationFeedback 不覆盖、不删除。
保留两条原始证据。
标记为“难度感受发生变化”或“难度感受不稳定”。
近期反馈权重更高。
不直接修改 mastery。
```

例子：

```text
7 月 1 日：q_frac_001 太难
7 月 12 日：q_frac_001 太简单

长期画像候选：
  学生对该题 / 该知识点的难度感受发生变化，近期更倾向觉得偏简单。
```

核心规则：

```text
换题是结构化推荐反馈。
它记录原因、重排或重选题、刷新 current_question。
它影响推荐，不影响掌握度。
最近至少保留 10 条换题反馈。
```

## 9. 学生对当前题问 Agent 要提示

场景：

```text
页面当前题是 q_frac_018。
学生还没有提交答案。
学生在 Agent 侧边栏问：这题怎么做？
```

这一步是 Agent 对话。

它不是：

```text
不是提交答案。
不是换题。
不是推荐下一题。
不是系统主动追问学生。
```

核心规则：

```text
Agent 可以讲思路、给提示、解释题意。
但默认不直接替学生完成整题。
除非学生明确点了“查看答案”，或者当前题已经进入答案讲解状态。
```

流程：

```text
学生发消息
-> 识别意图：要提示 / 要讲思路 / 看不懂题
-> 读取 current_question
-> 读取当前题状态：未提交 / 已提交 / 已看答案
-> 读取最新 TeachingState
-> 读取当前 conversation 的短期记忆
-> 按需读取学生长期画像
-> 按需读取题目解析 / 知识点资料
-> 生成 Agent 回复
-> 保存学生输入 + AI 完整回复
-> 记录 TeachingTrace
```

如果当前题还没提交，Agent 回复应该偏提示。

回复方式：

```text
先帮学生理解题意。
再指出这题用到哪个知识点。
再给第一步或关键突破口。
必要时问一句：你想要下一步提示，还是想自己先试一下？
```

这里的“问一句”只是 Agent 回复内容，不是系统主动发起对话。

也就是说：

```text
Agent 不会自己跳出来问学生。
只有学生先问，Agent 才回复。
```

这一步可以写入：

```text
student_message
ai_full_reply
used_context
TeachingTrace
当前 conversation 的短期记忆
```

这一步不写入：

```text
不更新 KT。
不改变 mastery。
不切换 current_question。
不推荐下一题。
不写 recommendation_history。
不直接写长期画像。
```

原因：

```text
学生只是问了提示，还没有作答。
问提示可以说明学生当前需要帮助，但不能证明他会或不会。
```

长期画像可以之后后台提炼，但不能单次直接写死。

例子：

```text
如果学生多次在分数约分题上问“看不懂题意”，
后台可以提炼成：
学生在分数约分题的题意理解上经常需要提示。
```

核心规则：

```text
学生问当前题时，Agent 只围绕 current_question 回复。
它可以用短期记忆和长期画像来调整讲法。
它记录完整问答。
它不更新掌握度，也不切题。
```

## 10. 学生把答案发到 Agent 里

场景：

```text
页面当前题是 q_frac_018。
学生还没点击“提交答案”。
学生在 Agent 里说：答案是不是 3/4？
```

这一步是 Agent 对话。

默认不算正式提交。

原因：

```text
学生可能是在猜答案。
学生可能是在问思路。
学生可能是在让 Agent 检查一步。
学生可能还没决定正式提交。
```

如果把 Agent 聊天里的答案直接当成正式提交，容易误判学生状态。

例如：

```text
学生随口问：是不是 3/4？
系统却当成正式提交，更新掌握度。
```

这是不允许的。

### 10.1 正常流程

流程：

```text
学生发消息
-> 识别意图：答案确认 / 解题尝试 / 步骤检查
-> 读取 current_question
-> 读取当前题状态
-> 读取题目标准答案 / 解析
-> 读取最新 TeachingState
-> 读取当前 conversation 的短期记忆
-> Agent 判断学生这句话是否合理
-> 回复学生
-> 保存学生输入 + AI 完整回复
-> 记录 TeachingTrace
```

Agent 可以做：

```text
可以判断这个答案是否接近正确。
可以指出哪里对、哪里错。
可以提示下一步怎么修正。
可以说“如果你确定，可以点击页面上的提交按钮。”
```

但这一步不做：

```text
不写 answer_submitted。
不生成正式 grading_result。
不更新 KT。
不改变 mastery。
不切换 current_question。
不触发下一题推荐。
```

### 10.2 聊天答案怎么记录

Agent 聊天里的答案按“草稿 / 讨论”处理。

可以记录：

```text
student_message：答案是不是 3/4？
ai_full_reply：你的方向接近，但分母处理还差一步...
TeachingTrace：学生在当前题中尝试给出答案
conversation_short_memory：本轮对话里学生尝试过 3/4
```

这个短期记忆可以在同一个对话框里继续使用。

例如学生下一句问：

```text
那我哪里错了？
```

Agent 可以接上刚才的 `3/4` 来解释。

### 10.3 和正式提交的区别

正式提交只能由页面“提交答案”按钮触发。

区别：

```text
Agent 聊天里的答案：
  草稿讨论。
  用于当前对话解释。
  不更新 KT / mastery。

页面提交答案：
  正式作答。
  生成 grading_result。
  更新 KT。
  编译新的 TeachingState。
```

### 10.4 长期画像怎么处理

长期画像也不能因为单次聊天答案直接写死。

不能这样写：

```text
学生不会分数约分。
学生掌握分数约分。
```

最多由后台之后根据多次类似记录提炼。

例如：

```text
学生多次在分数约分题中把最终化简漏掉。
```

核心规则：

```text
Agent 聊天里的答案默认是草稿讨论。
它可以被 Agent 用来回复和解释。
它会被记录为对话内容。
但它不等于正式提交，不更新 KT / mastery。
正式作答只能由“提交答案”按钮触发。
```

## 11. 学生在 Agent 里直接要答案

场景：

```text
页面当前题是 q_frac_018。
学生还没有点击“查看答案”。
学生在 Agent 里说：直接告诉我答案吧。
```

这时 Agent 不能直接回答答案。

核心规则：

```text
Agent 不能绕过“查看答案”按钮直接给答案。
学生要答案时，必须让学生点击页面上的“查看答案”按钮。
只有 answer_revealed = true 后，Agent 才能回答答案相关问题。
```

原因：

```text
查看答案必须通过页面按钮触发。
这样系统才能稳定记录：学生确实看过答案。
```

### 11.1 尚未查看答案时

流程：

```text
学生发消息
-> 识别意图：直接要答案 / 要完整解析 / 要标准答案
-> 读取 current_question
-> 读取当前题状态
-> 检查 answer_revealed 是否为 true
```

如果：

```text
answer_revealed = false
```

Agent 不能给标准答案，也不能给完整解析。

Agent 回复：

```text
如果你想看答案，请点击页面上的“查看答案”按钮。
看完之后，你可以继续问我，我可以帮你讲每一步为什么这么做。
```

这一步只记录普通对话：

```text
student_message
ai_full_reply
TeachingTrace
当前 conversation 的短期记忆
```

TeachingTrace 可以记：

```text
学生向 Agent 请求答案。
但当前题尚未查看答案。
Agent 未直接给出答案。
Agent 引导学生点击“查看答案”按钮。
```

这一步不写：

```text
不写 answer_revealed。
不更新 KT。
不改变 mastery。
不生成 grading_result。
不切换 current_question。
不推荐下一题。
不直接给标准答案。
不直接给完整解析。
```

### 11.2 学生点击“查看答案”后

如果学生点击页面“查看答案”按钮，就回到第 2 步。

流程：

```text
点击“查看答案”
-> 记录 answer_revealed
-> 页面展示答案 / 解析
```

之后如果学生再问 Agent：

```text
这一步为什么要这样做？
标准答案里这一步我没看懂。
为什么是 3/4？
```

此时：

```text
answer_revealed = true
```

Agent 才可以围绕答案回答。

流程：

```text
学生发消息
-> 识别意图：答案讲解 / 解析追问
-> 读取 current_question
-> 确认 answer_revealed = true
-> 读取题目答案 / 解析
-> 读取当前 conversation 短期记忆
-> 按需读取 TeachingState 和长期画像
-> 生成答案相关讲解
-> 保存学生输入 + AI 完整回复
-> 记录 TeachingTrace
```

这一步可以写入：

```text
student_message
ai_full_reply
used_context
TeachingTrace
当前 conversation 的短期记忆
```

这一步仍然不写：

```text
不更新 KT。
不改变 mastery。
不切换 current_question。
不推荐下一题。
```

原因：

```text
看答案后的追问，只能说明学生在理解答案。
还不能证明学生已经掌握。
```

核心规则：

```text
Agent 不能绕过“查看答案”按钮直接给答案。
学生要答案时，必须让学生点击“查看答案”按钮。
只有 answer_revealed = true 后，Agent 才能回答答案相关问题。
答案讲解会被记录，但不更新掌握度。
```

## 12. 提交前看完答案后直接下一题

场景：

```text
页面当前题是 q_frac_018。
学生没有提交答案。
学生点击了“查看答案”。
系统已记录 answer_revealed = true，且 reveal_timing = before_submit。
学生看完答案后点击“下一题”。
```

这时允许进入下一题。

但是状态不是：

```text
学生答对了。
学生答错了。
学生掌握了。
学生不会。
```

而是：

```text
学生看过答案后跳过本题。
```

### 12.1 按钮前置条件

“下一题”按钮允许进入下一题的条件：

```text
当前题已有 answer_submitted。
或当前题已有 answer_revealed。
```

也就是说：

```text
提交过答案 -> 可以进入下一题。
看过答案 -> 可以进入下一题。
既没提交，也没看答案 -> 不允许进入下一题。
```

如果既没提交也没看答案，提示：

```text
请先提交答案，或者查看答案后再进入下一题。
```

### 12.2 看答案后跳过的流程

流程：

```text
点击下一题按钮
-> 检查当前题状态
-> 发现 answer_submitted = false
-> 发现 answer_revealed = true
-> 确认 reveal_timing = before_submit
-> 记录 skipped_after_reveal
-> 读取最新 TeachingState
-> 读取最近作答历史
-> 读取最近 10 条换题反馈
-> 读取题库候选摘要
-> 按需读取学生长期画像
-> Recommender 选择下一题
-> 更新 current_question
-> 保存 recommendation_history
-> 页面刷新到下一题
-> 记录 TeachingTrace
```

这里要特别注意：

```text
不生成 grading_result。
不更新 KT。
不改变 mastery。
```

因为学生没有作答。

### 12.3 对推荐的影响

推荐下一题时，可以参考这件事：

```text
学生提交前看答案，并跳过了当前题。
```

推荐倾向可以更保守一点：

```text
优先推荐同知识点更基础 / 相近难度的题。
不要直接提高难度。
不要把这题当成已掌握。
```

这一步可以写入：

```text
answer_revealed 已存在，且 reveal_timing = before_submit
skipped_after_reveal
recommendation_history
current_question
TeachingTrace
```

TeachingTrace 至少记录：

```text
原 current_question
是否提交答案：否
是否查看答案：是
查看答案时机：提交前
跳过原因：看答案后进入下一题
下一题推荐依据
新 current_question
```

这一步不写入：

```text
不写 answer_submitted。
不生成 grading_result。
不更新 KT。
不改变 mastery。
不写长期画像。
```

长期画像只能后台之后根据多次行为提炼。

例如：

```text
学生多次看答案后直接跳过分数题。
```

但单次不能写成：

```text
学生不会分数。
```

核心规则：

```text
学生提交前看过答案后，可以进入下一题。
但这不是正式作答。
系统记录为“看答案后跳过本题”。
它影响推荐保守程度，不影响掌握度。
如果学生是提交后才查看答案，只是看解析，不触发保守推荐。
```

## 13. 提交前看过答案后提交答案

场景：

```text
页面当前题是 q_frac_018。
学生先点击了“查看答案”。
系统已记录 answer_revealed = true，且 reveal_timing = before_submit。
学生又在答题框里填写答案，并点击“提交答案”。
```

这时可以允许提交。

但这不是独立完成。

系统要标记为：

```text
看答案后的提交。
```

### 13.1 正常流程

流程：

```text
点击提交答案
-> 读取 current_question
-> 检查 answer_revealed 是否为 true
-> 检查 reveal_timing 是否为 before_submit
-> 收集学生提交内容
-> 生成 answer_submitted
-> 判题，生成 grading_result
-> 标记 submitted_after_reveal = true
-> 页面显示正确 / 错误 / 解析提示
-> 保存记录
-> 记录 TeachingTrace
```

这里可以生成：

```text
answer_submitted
grading_result
submitted_after_reveal
TeachingTrace
```

但是不更新 KT。

也就是说：

```text
可以判对错。
可以记录学生提交了什么。
可以用于当前页面反馈。
但不能用它证明学生掌握了。
```

### 13.2 为什么不更新 KT

因为学生已经看过答案。

如果这时提交正确：

```text
不能说明学生独立会做。
可能只是照着答案写。
```

如果这时提交错误：

```text
也不能简单说明学生不会。
可能是抄错、输入错、理解到一半。
```

所以最稳的规则是：

```text
提交前看答案后的提交，不更新 KT。
不改变 mastery。
```

### 13.3 对推荐的影响

这一步对推荐可以有轻微影响。

例如：

```text
学生看答案后还能提交错：
  下一题推荐更基础 / 更慢一点。

学生看答案后提交正确：
  不直接提高难度。
  可以继续给相近题确认是否真正掌握。
```

但这种影响应该走推荐记录，不走 mastery。

### 13.4 写入和不写入

这一步可以写入：

```text
answer_submitted
grading_result
submitted_after_reveal
TeachingTrace
当前题状态
```

TeachingTrace 至少记录：

```text
提交前是否已查看答案：是
学生提交内容
判题结果
是否更新 KT：否
原因：看答案后的提交不能作为独立掌握证据
```

这一步不写入：

```text
不更新 KT。
不改变 mastery。
不写长期画像。
不自动推荐下一题。
不自动切换 current_question。
```

长期画像也不能单次写死。

只能后台多次提炼。

例如：

```text
学生多次看答案后仍提交错误。
```

但不能单次写成：

```text
学生不会这个知识点。
```

核心规则：

```text
看答案后可以提交答案。
系统可以判题，也可以记录提交内容。
但必须标记 submitted_after_reveal = true。
这类提交不更新 KT / mastery。
它只能作为推荐参考和后续分析证据。
```

## 14. 学生新开一个 Agent 对话框

场景：

```text
学生当前还在同一个学习页面。
current_question 仍然是 q_frac_018。
学生关闭 / 新开了一个 Agent 对话框。
新的 conversation_id 生成。
```

这一步不是换题，也不是重新开始学习。

它只是：

```text
开启一个新的对话上下文。
```

核心规则：

```text
短期记忆按 conversation_id 隔离。
长期画像、KT、学习事实、推荐历史按 student_id 共享。
```

也就是说：

```text
新对话框的短期记忆是空的。
但学生长期画像还在。
当前题 current_question 还在。
KT 状态还在。
历史作答记录还在。
换题反馈还在。
推荐历史还在。
```

### 14.1 新开对话框流程

流程：

```text
学生新开 Agent 对话框
-> 创建新的 conversation_id
-> 初始化当前 conversation 的短期记忆
-> 不改变 current_question
-> 不改变 TeachingState
-> 不改变 KT
-> 不改变 mastery
-> 不切题
-> 不推荐新题
```

如果学生在新对话框里问：

```text
这题怎么做？
```

Agent 读取：

```text
current_question
当前题状态
最新 TeachingState
当前 conversation 的短期记忆：新对话，所以为空
学生级长期画像
历史作答 / 推荐记录
按需读取题目解析
```

然后按第 9 步的规则回复。

### 14.2 旧短期记忆不会直接带过来

这里要特别注意：

```text
旧对话框里的短期记忆不会直接带到新对话框。
```

例如旧对话框里学生说过：

```text
我刚才试了 3/4。
```

如果新开对话框，新的短期记忆里默认没有这句话。

但如果这句话已经作为正式学习事实保存，例如：

```text
answer_submitted
grading_result
answer_revealed
RecommendationFeedback
```

那新对话框可以通过学习事实读取到。

### 14.3 写入和不写入

这一步可以写入：

```text
conversation_id
conversation_started_at
```

这一步不写入：

```text
不写 answer_submitted。
不写 answer_revealed。
不更新 KT。
不改变 mastery。
不切换 current_question。
不写 recommendation_history。
不写长期画像。
```

长期画像不会因为“新开对话框”变化。

核心规则：

```text
新开对话框只重置当前对话的短期记忆。
它不重置学习状态。
current_question、KT、长期画像、学习事实、推荐历史仍然共享。
```

## 15. 后台提炼长期画像 / 长期记忆

场景：

```text
学生已经做过几道题。
学生有提交答案、查看答案、换题反馈、Agent 对话记录。
系统后台开始整理这些记录。
```

这一步不是学生点击按钮，也不是 Agent 正在回复学生。

它是后台在已有记录里做整理。

核心规则：

```text
长期画像不能凭单次行为直接写死。
长期画像只能从多次记录里提炼趋势。
原始记录永远保留，不被长期画像覆盖。
```

### 15.1 后台可以读取什么

后台可以读取：

```text
answer_submitted
grading_result
answer_revealed
skipped_after_reveal
submitted_after_reveal
RecommendationFeedback
student_message
ai_full_reply
TeachingTrace
recommendation_history
KT 状态
```

注意这里包括：

```text
AI 完整回复也会被读取。
```

但 AI 回复的作用是辅助理解上下文，不是直接证明学生会不会。

例如不能因为 AI 讲过一次“通分方法”，就写：

```text
学生已经掌握通分。
```

也不能因为 AI 说“你这里错了”，就直接写：

```text
学生不会通分。
```

### 15.2 后台提炼流程

流程：

```text
后台任务启动
-> 读取最近一段时间的学习记录和对话记录
-> 按知识点 / 题型 / 行为类型归类
-> 查找重复出现的模式
-> 判断是否足够稳定
-> 生成长期画像候选
-> 关联证据来源
-> 写入 memory_update 记录
-> 更新学生长期画像
```

长期画像候选例子：

```text
学生多次在分数约分题中漏掉最终化简。
学生最近多次反馈推荐题偏难。
学生对应用题题意理解经常需要提示。
学生看答案后直接跳过分数题的次数较多。
```

但不能写成：

```text
学生不会分数。
学生已经掌握分数。
学生不喜欢数学。
学生不适合做应用题。
```

这些太绝对。

### 15.3 新旧画像冲突时

如果新旧画像冲突，比如：

```text
以前：学生觉得分数题偏难。
现在：学生最近多次反馈分数题太简单。
```

不直接删除旧记录。

应该写成：

```text
学生对分数题的难度感受发生变化。
近期更倾向认为当前推荐的分数题偏简单。
```

也就是说：

```text
旧证据保留。
新趋势更新。
近期记录权重更高。
```

### 15.4 写入和不写入

这一步可以写入：

```text
long_term_profile
memory_update
profile_evidence_links
profile_confidence
updated_at
```

这一步不写入：

```text
不更新 KT。
不改变 mastery。
不切换 current_question。
不推荐下一题。
不生成 Agent 回复。
不删除原始学习记录。
```

原因：

```text
长期画像是对历史行为的总结。
它不是一次新的作答。
它不能直接改变掌握度。
```

### 15.5 后续怎么使用长期画像

之后长期画像可以被使用在：

```text
Agent 回复时调整讲法。
Recommender 推荐题目时调整倾向。
TeachingPlanner 决定讲法时作为背景参考。
```

但它仍然不是最高优先级证据。

优先级大概是：

```text
当前题状态 > 最新作答事实 > TeachingState > 最近学习记录 > 长期画像
```

核心规则：

```text
长期画像是后台从多次记录中提炼出来的趋势。
它必须带证据来源。
它不覆盖原始记录。
它不更新 KT / mastery。
AI 回复会被记录和读取，但 AI 回复本身不能证明学生掌握或没掌握。
```

## 16. 学生在 Agent 里要求换知识点或出题

场景：

```text
页面当前题是 q_frac_018。
学生在 Agent 里说：我不想练分数了，给我换一道几何题。
```

或者：

```text
学生说：你直接给我出一道相似题。
```

这里要区分两种东西：

```text
Agent 对话里的建议
页面上的正式 current_question
```

核心规则：

```text
Agent 不能直接切换 current_question。
正式题目切换必须通过页面按钮或结构化入口完成。
```

原因：

```text
current_question 是页面状态。
它会影响作答记录、查看答案、提交答案、推荐历史、TeachingTrace。
如果 Agent 随口生成一道题并当成 current_question，状态会乱。
```

### 16.1 学生要求换知识点

如果学生说：

```text
给我换个知识点。
```

Agent 可以回复建议：

```text
可以。你现在如果想换知识点，可以在练习设置里选择知识点，或者点击“下一题”让系统按你的当前状态推荐。
```

如果页面有“选择知识点 / 练习设置”按钮，可以引导学生去点。

但 Agent 不做：

```text
不直接更新 current_question。
不直接写 recommendation_history。
不直接生成正式题目。
不切换页面。
```

### 16.2 学生要求 Agent 出题

如果学生说：

```text
给我出一道相似题。
```

这里有两种方案。

方案 A：严格方案，推荐。

Agent 不直接出正式题。

回复：

```text
如果你想继续练相似题，可以点击“下一题”按钮。
系统会基于你当前状态推荐下一道题。
```

优点：

```text
状态最干净。
所有正式题目都来自题库和推荐模块。
作答、查看答案、提交答案都能完整记录。
```

缺点：

```text
对学生来说没那么灵活。
```

方案 B：允许 Agent 出“临时练习题”。

Agent 可以临时生成一道题，但必须标记为：

```text
临时题
非 current_question
不进入正式作答流程
不更新 KT
不参与 recommendation_history
```

这种题只能用于解释或练习，不作为正式题库题。

缺点是很容易和正式题混淆，所以先不采用。

当前采用方案 A：

```text
Agent 不直接出正式题。
Agent 可以解释、建议、引导学生点击结构化按钮。
正式题目只由题库 / 推荐模块产生。
current_question 只由页面结构化动作修改。
```

### 16.3 对话流程

流程：

```text
学生发消息
-> 识别意图：想换知识点 / 想让 Agent 出题
-> 读取 current_question
-> 读取当前题状态
-> 读取 TeachingState
-> 读取当前 conversation 短期记忆
-> 按需读取长期画像
-> Agent 给出建议或引导
-> 保存学生输入 + AI 完整回复
-> 记录 TeachingTrace
```

这一步可以写入：

```text
student_message
ai_full_reply
TeachingTrace
当前 conversation 的短期记忆
```

这一步不写入：

```text
不更新 current_question。
不写 recommendation_history。
不生成正式题目。
不更新 KT。
不改变 mastery。
不切换页面。
不写长期画像。
```

### 16.4 未来支持指定知识点练习

如果未来要支持“指定知识点练习”，最好单独做一个结构化入口。

例如：

```text
选择知识点按钮
练习设置面板
按知识点开始练习按钮
```

那时候流程应该是：

```text
学生选择知识点
-> 系统记录 practice_preference
-> Recommender 从该知识点选题
-> 更新 current_question
-> 写 recommendation_history
```

而不是让 Agent 自己直接改页面题目。

核心规则：

```text
Agent 可以理解学生想换知识点或想出题。
但 Agent 不直接切换 current_question。
正式题目必须来自题库 / 推荐模块。
current_question 只能由页面结构化动作修改。
```

## 17. 学习过程中通过页面切换知识点

场景：

```text
页面当前题是 q_frac_018。
学生正在练习分数加法。
学生现在不想继续练分数。
学生回到首页。
首页展示“继续学习”和“探索新知识点”。
```

这一步是页面结构化动作，不是 Agent 对话。

核心规则：

```text
页面结构化入口可以改变 current_question。
Agent 不能直接改变 current_question。
首页展示分为：继续学习 / 探索新知识点。
继续学习 / 探索新知识点按是否有 learning_state_by_concept 判断，不按 mastery 判断。
继续学习里的知识点点击后直接继续学习。
探索新知识点里的知识点点击后才进入首次设置。
中途切换知识点时，要保存原知识点的学习状态。
下次切回同一知识点时，要参考该知识点最新状态继续推荐。
```

注意：

```text
继续学习 ≠ 已掌握。
继续学习只表示学生曾经开始过这个知识点。
```

### 17.1 首页知识点分区

首页分两块：

```text
继续学习：
  分数加法
  长方形面积
  乘法原理

探索新知识点：
  方程
  比例
  图形剪拼
```

判断规则：

```text
有 learning_state_by_concept = 继续学习。
没有 learning_state_by_concept = 探索新知识点。
```

这里不看：

```text
mastery 高不高。
KT 是否已经稳定。
学生是否真正掌握。
```

### 17.2 点击继续学习里的知识点

如果学生点击首页“继续学习”里的知识点：

```text
继续学习：分数加法
```

系统不重新问：

```text
不重新问初次学习 / 复习 / 正在练习。
不重新问已接触过哪些相关知识点。
不重新做 onboarding。
```

流程：

```text
学生点击继续学习里的知识点
-> 检查当前题是否已经结束
-> 保存当前知识点 learning_state_by_concept
-> 读取被点击知识点的 learning_state_by_concept
-> 读取该知识点最新 KT
-> 读取该知识点最近作答 / 换题 / 跳过 / 查看答案记录
-> Recommender 根据该知识点最新状态选题
-> 更新 current_question
-> 写 recommendation_history
-> 页面进入新题
-> 记录 TeachingTrace
```

这样系统不是重新开始，而是接着该知识点的最新状态推荐。

例子：

```text
学生上次在分数加法连续答错。
-> 这次切回来，推荐更基础的分数加法题。

学生上次在分数加法已经连续答对基础题。
-> 这次切回来，可以推荐稍微进阶一点。

学生上次对分数加法反馈“太难”。
-> 这次切回来，推荐更保守。

学生上次提交前看答案后跳过。
-> 这次切回来，不当作掌握，推荐相近基础题。
```

### 17.3 点击探索新知识点：首次设置

如果学生点击首页“探索新知识点”里的知识点：

```text
开始学习：几何 / 长方形面积
```

这才进入首次设置。

流程：

```text
学生点击探索新知识点里的知识点
-> 检查当前题是否已经结束
-> 保存当前知识点 learning_state_by_concept
-> 勾选已接触过的相关知识点
-> 选择学习状态：初次学习 / 复习 / 正在练习
-> 系统记录 practice_preference
-> 初始化该知识点 learning_state_by_concept
-> Recommender 根据新偏好选第一题
-> 更新 current_question
-> 写 recommendation_history
-> 页面进入新题
-> 记录 TeachingTrace
```

`practice_preference` 可以记录：

```text
student_id
session_id
selected_knowledge_point
prior_exposure_concepts
learning_entry_mode：first_learn / review / practicing
source：homepage_unlearned_concept
created_at
```

这一步仍然不能写成：

```text
勾选接触过 = 已掌握。
选择复习 = 已掌握。
选择正在练习 = 已掌握。
```

### 17.4 保存原知识点状态

学生离开一个知识点时，不能把这个知识点的进度丢掉。

系统要保存：

```text
learning_state_by_concept
```

它表示：

```text
这个学生在这个知识点下，最近学到哪里了。
```

可以记录：

```text
student_id
concept_id
last_current_question
last_question_status
recent_answer_history
recent_recommendation_history
recent_feedback_history
KT 状态
TeachingState 摘要
last_learning_entry_mode
updated_at
```

这不是新的长期画像。

它更像是：

```text
按知识点保存的学习进度快照。
```

### 17.5 当前题已经结束

当前题满足：

```text
已有 answer_submitted
或已有 answer_revealed
```

那可以直接切换。

流程：

```text
读取当前题状态
-> 确认当前题已结束
-> 保存原知识点 learning_state_by_concept
-> 根据首页点击的知识点推荐题目
-> 更新 current_question
```

### 17.6 当前题还没结束

当前题满足：

```text
没有 answer_submitted
也没有 answer_revealed
```

这时不能悄悄切走。

页面要提示：

```text
当前题还没有提交或查看答案。
切换知识点会放弃当前题，是否继续？
```

如果学生取消：

```text
不切题。
不写 practice_preference。
不写 recommendation_history。
current_question 不变。
```

如果学生确认：

```text
记录 abandoned_current_question
保存原知识点 learning_state_by_concept
如果点击的是探索新知识点，继续首次设置
如果点击的是继续学习里的知识点，读取旧 learning_state_by_concept
Recommender 选目标知识点题目
更新 current_question
写 recommendation_history
记录 TeachingTrace
```

`abandoned_current_question` 可以记录：

```text
question_id：原 current_question
reason：practice_setting_changed
answer_submitted：false
answer_revealed：false
created_at
```

放弃当前题不代表学生不会：

```text
不更新 KT。
不改变 mastery。
不写成学生不会当前题。
```

### 17.7 探索新知识点下怎么选第一题

如果选择“初次学习”：

```text
从低难度 / 入门题开始。
不急着判断掌握度。
```

如果选择“复习”：

```text
先给 2-3 道短诊断题。
了解学生还记得多少。
```

如果选择“正在练习”：

```text
先给 2-3 道代表题。
定位当前练习水平。
```

如果这个知识点已经在继续学习里：

```text
优先参考 learning_state_by_concept。
不要重新走首次设置。
```

### 17.8 写入和不写入

这一步可以写入：

```text
practice_preference
learning_state_by_concept
abandoned_current_question（如果当前题未结束且学生确认切换）
recommendation_history
current_question
TeachingTrace
```

TeachingTrace 至少记录：

```text
原 current_question
原知识点
目标知识点
目标知识点来自继续学习还是探索新知识点
当前题是否已结束
是否放弃未结束题目
是否读取旧知识点 learning_state_by_concept
推荐依据
新 current_question
```

这一步不写入：

```text
不因为切换知识点更新 KT。
不因为离开知识点改变 mastery。
不清空该知识点历史状态。
不把点击继续学习里的知识点当成新学生初始化。
不因为进入探索新知识点就写学生不会。
不写长期画像结论。
不生成 Agent 回复。
```

核心规则：

```text
学习过程中切换知识点，走首页结构化入口。
首页分为继续学习和探索新知识点。
继续学习 / 探索新知识点按是否有 learning_state_by_concept 判断，不按 mastery 判断。

点击继续学习里的知识点：
  直接继续学习。
  读取 learning_state_by_concept。
  不重新选择学习状态。
  不重新勾选已接触过相关知识点。

点击探索新知识点里的知识点：
  进入首次设置。
  勾选已接触过的相关知识点。
  选择初次学习 / 复习 / 正在练习。

它可以更新 current_question。
但选择知识点 / 学习状态不是掌握证据。
如果当前题未结束，切换前要确认并记录 abandoned_current_question。

中途换知识点时，要保存原知识点的学习状态。
下次切回同一知识点时，必须参考该知识点最新状态继续推荐。
切换知识点本身不更新 KT / mastery。
```

## 18. 知识点阶段推进

场景：

```text
学生正在练习分数加法。
已经独立提交了几道题。
系统有 grading_result、KT、换题反馈、跳过记录。
```

这一步不是学生点击按钮，也不是 Agent 对话。

它是系统在学生作答后更新知识点内部学习阶段。

通常可以在每次正式提交答案后触发。

核心规则：

```text
继续学习 / 探索新知识点只决定首页分区。
知识点掌握阶段由 learning_state_by_concept 里的 phase 表示。
```

### 18.1 phase 字段

`learning_state_by_concept.phase` 可以包含：

```text
started          刚开始
diagnosing       正在了解水平
practicing       正在练习
consolidating    巩固中
ready_for_mixed  可以开始融合题
```

这里先不使用：

```text
completed
```

原因：

```text
数学知识点不是做完就永久完成。
```

推荐使用：

```text
ready_for_mixed
```

它表示：

```text
这个知识点已经有一定基础，可以和其他知识点组合练。
```

但它不表示：

```text
学生已经完全掌握。
```

### 18.2 阶段怎么变化

初次进入探索新知识点里的知识点时：

```text
phase = started
```

如果选择“复习 / 正在练习”，并且系统安排 2-3 道了解水平题：

```text
phase = diagnosing
```

学生完成短诊断后：

```text
如果表现较弱 -> phase = practicing
如果表现不错 -> phase = consolidating
```

学生在基础题 / 相近题上表现稳定后：

```text
phase = ready_for_mixed
```

### 18.3 判断 ready_for_mixed 的条件

不要只看一题答对。

可以用简单规则：

```text
最近独立提交题 >= 3
最近正确率不错
没有连续提交前看答案后跳过
没有多次反馈太难
KT confidence 不再是 low
```

例如：

```text
最近 3 道未看答案提交，答对 2 道以上。
并且没有最近 2 次都反馈太难。
并且没有连续跳过。
```

就可以进入：

```text
ready_for_mixed
```

但这仍然不是“完全掌握”。

它只是表示：

```text
可以尝试融合题。
```

### 18.4 阶段可以回退

阶段不是证书。

阶段是推荐策略状态。

如果学生已经进入：

```text
ready_for_mixed
```

之后连续错融合题，或者频繁反馈太难：

```text
phase 回到 consolidating 或 practicing
```

也就是说：

```text
phase 可以随着后续表现前进或回退。
```

### 18.5 写入和不写入

这一步可以写入：

```text
learning_state_by_concept.phase
phase_reason
phase_evidence
updated_at
TeachingTrace
```

`phase_evidence` 可以包括：

```text
最近独立提交题数
最近正确率
是否提交前看答案后跳过
是否多次换题反馈太难
KT confidence
```

这一步不写入：

```text
不写长期画像结论。
不切换 current_question。
不自动推荐下一题。
不因为 phase = ready_for_mixed 就写 mastery = 1。
```

原因：

```text
phase 只是推荐策略状态。
mastery 是 KT 估计。
二者相关，但不是同一个东西。
```

核心规则：

```text
首页继续学习 / 探索新知识点只看有没有 learning_state_by_concept。
知识点内部还要有 phase。
phase 用来决定当前适合基础题、巩固题，还是融合题。
ready_for_mixed 表示可以尝试融合题，不表示完全掌握。
phase 可以随着后续表现前进或回退。
```

## 19. 单知识点题与融合题

场景：

```text
系统准备从题库里推荐下一题。
候选题里有些题只考一个知识点。
有些题同时涉及多个知识点。
```

题目先分成两大类：

```text
单知识点题
融合题
```

核心规则：

```text
单知识点题用于学习、诊断、巩固。
融合题用于综合运用。
phase 决定融合题权重。
融合题做错后，优先拆回单知识点题诊断。
```

### 19.1 单知识点题

定义：

```text
主要考一个知识点。
适合初次学习、短诊断、基础练习、巩固。
```

在 XES3G5M 里可以先用规则识别：

```text
kc_routes 只有 1 条。
或多条 kc_routes 其实是同一个叶子知识点在不同分类体系下重复出现。
```

例如：

```text
知识点 -> 几何模块 -> ... -> 长方形面积公式
拓展思维 -> 几何模块 -> ... -> 长方形面积公式
```

这种虽然有两条路径，但叶子知识点一样，可以仍然算单知识点题。

### 19.2 融合题

定义：

```text
同时涉及多个不同知识点。
需要学生把多个知识点一起用。
适合巩固后、ready_for_mixed 后、综合练习。
```

在 XES3G5M 里可以先用规则识别：

```text
kc_routes 有多条。
并且叶子知识点不同。
```

例如一题同时涉及：

```text
加乘原理综合
物品搭配
```

就算融合题。

题目元数据可以增加：

```text
question_scope:
  single_concept
  mixed_concept
```

### 19.3 推荐策略

初次学习：

```text
只推荐单知识点题。
不推荐融合题。
```

复习：

```text
先用单知识点题了解水平。
表现不错后，少量加入轻融合题。
```

正在练习：

```text
可以先用单知识点题 + 少量融合题定位水平。
如果学生状态好，融合题比例逐步上升。
```

ready_for_mixed：

```text
可以正式推荐融合题。
```

如果学生频繁反馈太难、连续跳过、或者融合题连续错误：

```text
降低融合题权重。
回到单知识点题巩固。
```

### 19.4 融合题做错后怎么处理

融合题做错时，不能直接判定所有相关知识点都不会。

例如融合题涉及：

```text
A 知识点
B 知识点
```

学生做错后，系统可以：

```text
先推荐 A 的单知识点题。
再推荐 B 的单知识点题。
看是哪一块不稳。
```

这样做的目的：

```text
把综合错误拆开诊断。
避免粗暴更新所有知识点 mastery。
```

### 19.5 KT 更新规则

单知识点题：

```text
如果是未看答案前的正式提交，
可以主要更新这个知识点的 KT。
```

融合题：

```text
如果是未看答案前的正式提交，
可以作为多个相关知识点的证据。
但更新要更谨慎。
```

做对融合题：

```text
可以提高相关知识点的信心。
但不要一下子把所有知识点都拉很高。
```

做错融合题：

```text
不要直接判定所有相关知识点都不会。
优先记录 mixed_question_error。
后续用单知识点题拆解诊断。
```

### 19.6 写入和不写入

这一步可以写入：

```text
question_scope
mixed_concept_ids
mixed_question_error
recommendation_history
TeachingTrace
```

这一步不写入：

```text
不因为题目是融合题就直接提高难度。
不因为融合题答对就写所有知识点完全掌握。
不因为融合题答错就写所有知识点不会。
```

核心规则：

```text
题目分为单知识点题和融合题。
单知识点题用于学习、诊断、巩固。
融合题用于综合运用。
只有相关知识点进入 consolidating / ready_for_mixed 后，融合题权重才提高。
融合题做错后，优先拆回单知识点题诊断。
```

## 20. 融合题做错后的学生自选错因知识点

场景：

```text
学生做了一道融合题。
融合题涉及 A、B、C 三个知识点。
学生未看答案前正式提交。
系统判定错误。
学生点击查看答案，看了解析。
这次查看答案发生在正式提交之后，所以 reveal_timing = after_submit。
学生点击下一题。
```

这时不要直接进入下一题。

系统先让学生选择：

```text
这道题你觉得主要卡在哪个知识点？
```

核心规则：

```text
融合题做错后，学生看完解析并点击下一题时，
系统让学生选择主要卡住的知识点。
这个选择影响下一题推荐和解析重点，
但不直接更新 KT / mastery。
真正的掌握判断仍靠后续单知识点题的正式提交。
这里的查看解析是提交后查看，不触发保守推荐。
```

### 20.1 弹出错因知识点选择框

选项来自这道融合题的 `mixed_concept_ids`：

```text
A 知识点
B 知识点
C 知识点
我不确定
其他：自由输入
```

如果学生选择某个知识点：

```text
记录学生认为自己主要卡在这个知识点。
下一题优先回到这个知识点的单知识点题。
解析总结重点放在这个知识点。
```

如果学生选择：

```text
我不确定
```

系统可以：

```text
先推荐最基础 / 最可能薄弱的相关单知识点题。
```

如果学生填写其他：

```text
先记录自由输入。
系统能解析就映射到相关知识点。
解析不了就按“不确定”处理。
```

### 20.2 记录 mixed_error_self_diagnosis

学生选择后，系统记录：

```text
mixed_error_self_diagnosis
```

可以包含：

```text
question_id
mixed_concept_ids
selected_concept_id
reason_text
student_id
session_id
created_at
```

这里的 `selected_concept_id` 只是学生自我判断。

它不是确定错因。

### 20.3 生成针对选择的解析总结

学生选择后，系统可以给一个简短解析总结。

例如：

```text
你这题主要卡在 B 知识点。
这一步需要先用 B 的规则处理……
```

这个总结可以帮助学生把融合题拆开理解。

但注意：

```text
这不是 Agent 自由对话。
这是页面结构化流程里的简短总结。
```

如果后续学生继续问：

```text
为什么这里用 B？
```

才进入 Agent 对话流程。

### 20.4 下一题推荐

推荐模块读取：

```text
当前 TeachingState
原融合题
mixed_concept_ids
mixed_error_self_diagnosis
最近作答历史
最近换题反馈
learning_state_by_concept
KT 状态
题库候选
```

如果学生选择了 B 知识点：

```text
Recommender 优先选择 B 的单知识点题。
```

如果学生选择“不确定”：

```text
Recommender 从相关知识点里选择更基础 / 更可能薄弱的单知识点题。
```

这一步的目标是：

```text
把融合题错误拆回单知识点练习。
```

### 20.5 流程

完整流程：

```text
融合题提交错误
-> 学生查看答案解析
-> 记录 answer_revealed，且 reveal_timing = after_submit
-> 学生点击下一题
-> 系统检测：当前题是 mixed_concept，且 grading_result = wrong
-> 弹出错因知识点选择框
-> 学生选择卡住的知识点 / 不确定 / 其他
-> 记录 mixed_error_self_diagnosis
-> 生成针对该选择的简短解析总结
-> Recommender 优先选择对应知识点的单知识点题
-> 更新 current_question
-> 写 recommendation_history
-> 记录 TeachingTrace
```

### 20.6 写入和不写入

这一步可以写入：

```text
mixed_question_error
mixed_error_self_diagnosis
recommendation_history
current_question
TeachingTrace
```

TeachingTrace 至少记录：

```text
原融合题
融合题涉及知识点
学生选择的卡点
是否看过解析
推荐下一题依据
新 current_question
```

这一步不写入：

```text
不直接更新 KT。
不直接改变 mastery。
不把学生自选卡点写成确定错因。
不自动写长期画像。
```

原因：

```text
学生可能判断不准。
自选卡点只能影响推荐和讲解重点。
真正的掌握判断仍靠后续单知识点题的正式提交。
```

## 21. 融合题做对后的处理

场景：

```text
学生做了一道融合题。
融合题涉及 A、B 两个知识点。
学生未看答案前正式提交。
系统判定正确。
```

核心规则：

```text
融合题做对是综合正向证据。
它可以提高相关知识点信心和融合题推荐权重。
但不能替代每个知识点的单独掌握证据。
连续稳定表现后，才逐步提高融合题比例。
```

### 21.1 正常流程

流程：

```text
融合题提交正确
-> 记录 grading_result = correct
-> 识别 mixed_concept_ids
-> 记录 positive_mixed_evidence
-> KT 引擎按更低权重使用 mixed_question_evidence
-> 更新 learning_state_by_concept.phase
-> 更新 mixed_practice_readiness
-> 保存 TeachingTrace
-> 页面显示正确
```

这里的关键是：

```text
融合题做对是强证据。
但不是所有相关知识点完全掌握的证明。
```

### 21.2 KT 更新规则

涉及的每个知识点都可以获得正向证据。

但权重低于单知识点题的直接证据。

这里先不写死具体数学权重。

先采用原则：

```text
单知识点题 = 直接证据。
融合题 = 综合证据，低权重分配到多个相关知识点。
具体权重由 KT 引擎实现决定。
TeachingTrace 必须记录本次使用的是 mixed_question_evidence。
```

区别：

```text
单知识点题答对：
  对该知识点是直接证据。

融合题答对：
  对多个知识点是综合正向证据。
  但不能证明每个知识点都单独稳定。
```

所以不能这样写：

```text
融合题做对 = A 完全掌握。
融合题做对 = B 完全掌握。
```

### 21.3 阶段和融合题权重

如果学生连续做对融合题：

```text
相关知识点 phase 可以保持或进入 ready_for_mixed。
融合题推荐权重可以上升。
```

如果只是第一次做对融合题：

```text
只记录为 positive_mixed_evidence。
不直接完成阶段。
不直接跳到更复杂融合题。
```

后续推荐可以：

```text
继续给相近融合题。
穿插单知识点巩固题。
如果连续正确，再提高融合题比例。
```

### 21.4 写入和不写入

这一步可以写入：

```text
positive_mixed_evidence
mixed_concept_ids
KT 更新记录
learning_state_by_concept.phase
mixed_practice_readiness
TeachingTrace
```

TeachingTrace 至少记录：

```text
原融合题
融合题涉及知识点
判题结果：正确
KT 是否更新
融合题证据权重
phase 是否变化
推荐策略是否调整
```

这一步不写入：

```text
不把所有相关知识点 mastery 直接设为 1。
不写“学生已经完全掌握这些知识点”。
不自动跳到更复杂融合题。
不写长期画像结论。
```

原因：

```text
融合题做对可以说明学生有综合运用能力。
但还不能替代每个知识点的单独掌握证据。
```

## 22. 推荐器决定单知识点题还是融合题

场景：

```text
学生点击“下一题”。
系统准备推荐下一道题。
候选题池里既有单知识点题，也有融合题。
```

核心规则：

```text
推荐器不是随机选题。
它先决定题目类型：单知识点题 or 融合题。
phase 决定基础比例。
最近表现会调整比例。
融合题比例可以升高，也可以降低。
推荐策略不等于掌握度更新。
```

### 22.1 先决定题目类型

推荐器先决定：

```text
question_scope = single_concept
```

或者：

```text
question_scope = mixed_concept
```

然后再到对应题池里选具体题目。

也就是说：

```text
先决定练单点还是综合。
再决定具体推荐哪一道题。
```

### 22.2 phase 对应基础比例

可以先用简单规则：

```text
started：
  单知识点题 100%

diagnosing：
  单知识点题 100%

practicing：
  单知识点题 90%
  融合题 10%以内，甚至先不推

consolidating：
  单知识点题 70%
  融合题 30%

ready_for_mixed：
  单知识点题 50%
  融合题 50%
```

这些比例不是死规则。

它只是推荐器的起点。

### 22.3 最近状态会调整比例

如果最近出现：

```text
连续答错
连续提交前看答案后跳过
多次反馈太难
融合题做错
```

就降低融合题比例。

例如：

```text
ready_for_mixed 原本可以 50% 融合题。
但最近融合题做错 + 反馈太难。
则临时降到 20% 或直接回到单知识点巩固。
```

如果最近出现：

```text
单知识点题稳定正确
融合题也能做对
很少换题
很少提交前看答案或跳过
```

就提高融合题比例。

例如：

```text
consolidating 原本 30% 融合题。
但最近单点题稳定正确。
可以小幅提高融合题比例。
```

### 22.4 推荐器读取什么

推荐器读取：

```text
learning_state_by_concept.phase
KT 状态
最近独立提交记录
最近正确率
answer_revealed
reveal_timing
skipped_after_reveal
submitted_after_reveal
RecommendationFeedback
mixed_error_self_diagnosis
positive_mixed_evidence
题库候选
```

其中：

```text
只有 reveal_timing = before_submit 且 skipped_after_reveal = true，
才降低下一题难度 / 更保守。

reveal_timing = after_submit，
只表示学生看了解析，不降低推荐难度。
```

输出：

```text
question_scope_decision
single_vs_mixed_ratio
候选题池
新的 current_question
推荐原因说明
```

### 22.5 写入和不写入

这一步可以写入：

```text
recommendation_strategy
question_scope_decision
single_vs_mixed_ratio
recommendation_history
TeachingTrace
```

TeachingTrace 至少记录：

```text
当前 phase
基础单题 / 融合题比例
最近表现调整
最终 question_scope
新 current_question
推荐原因
```

这一步不写：

```text
不更新 KT。
不改变 mastery。
不直接改变 phase。
```

原因：

```text
推荐策略只是决定下一题怎么选。
phase 由第 18 步规则更新。
KT / mastery 由正式作答更新。
```

## 23. 首页知识点展示

场景：

```text
学生打开首页。
系统要展示继续学习和探索新知识点。
```

核心规则：

```text
首页展示要帮助学生选择学习入口。
不能把内部 KT 判断赤裸裸展示成“你会 / 你不会”。
```

内部判断可以是：

```text
有 learning_state_by_concept
没有 learning_state_by_concept
```

页面展示叫：

```text
继续学习
探索新知识点
```

这样对学生更友好。

### 23.1 继续学习

“继续学习”展示有 `learning_state_by_concept` 的知识点列表。

它不是只能有一个知识点。

学生可能同时在多个知识点上练习，例如：

```text
继续学习：
  异分母分数加法
  长方形面积
  乘法原理
```

每个知识点可以显示：

```text
知识点名称
最近学习时间
当前阶段文案
下一步建议
```

阶段文案要温和，不要太绝对。

可以这样显示：

```text
started -> 刚开始
diagnosing -> 正在了解水平
practicing -> 正在练习
consolidating -> 正在巩固
ready_for_mixed -> 可以尝试综合题
```

不要显示：

```text
已掌握
不会
完成
失败
```

原因：

```text
这些词太像最终判断，容易误导学生。
```

### 23.2 探索新知识点

“探索新知识点”展示没有 `learning_state_by_concept` 的知识点。

可以按知识路径分组。

例如：

```text
计数模块
几何模块
计算模块
方程
```

学生点击后进入首次设置：

```text
勾选已接触过的相关知识点
选择初次学习 / 复习 / 正在练习
```

### 23.3 融合题入口

先不要单独放一个“融合题”大入口。

融合题应该由系统在推荐时根据 phase 自动加入。

页面最多显示：

```text
可以尝试综合题
```

但不要让学生直接选择：

```text
我要做融合题
```

原因：

```text
这样可以避免学生绕过基础状态，直接进入不适合的融合题。
```

### 23.4 写入和不写入

这一步可以写入：

```text
home_knowledge_view
display_status
next_action_hint
```

这一步不写入：

```text
不更新 KT。
不改变 mastery。
不改变 current_question。
不写长期画像。
```

原因：

```text
首页展示只是入口展示。
它不是学习事件，也不是作答证据。
```

核心规则：

```text
首页内部按是否有 learning_state_by_concept 分组。
页面文案展示为继续学习 / 探索新知识点。
阶段展示要温和，不显示“你会 / 你不会”。
融合题不单独作为入口，由推荐器自动决定是否加入。
```
