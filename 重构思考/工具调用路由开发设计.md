# 工具调用路由开发设计

## 1. 文档目标

本文细化 MathTutor Agent 的工具调用路由模块。

这里的“路由”不是让大模型自由决定一切，而是解决四个具体问题：

```text
这次请求是什么事情；
这类事情允许使用哪些工具；
这些工具按照什么顺序执行；
工具失败以后如何降级，并且不能错误修改学习事实。
```

本文只设计可审计的系统执行过程，不记录或暴露 LLM（大语言模型）的内部思考内容。

与其他文档的分工：

- `思考链路.md`：描述完整场景和总体调用顺序。
- `上下文总设计.md`：描述哪些证据可以进入回复上下文。
- 本文：描述意图判断、工具过滤、执行计划、失败处理和代码迁移方式。

## 2. 当前代码现状

当前请求入口是：

```text
POST /events
-> MathTutorAgentRuntime.handle_event(...)
-> MathTutorLearningLoop.handle_event(...)
```

相关代码：

- `backend/app/api/events.py`
- `backend/app/runtime/agent_runtime.py`
- `backend/app/graph/learning_loop.py`
- `backend/app/runtime/context.py`
- `backend/app/runtime/capabilities.py`
- `backend/app/runtime/tools.py`

当前 `MathTutorAgentRuntime`（数学导师运行时）已经具备能力注册、工具注册、工具挂载记录和 TeachingTrace（教学追踪）汇总，但主要执行仍委托给 `MathTutorLearningLoop`（学习主循环）。

当前学习主循环基本固定执行：

```text
_load_context
-> _diagnose
-> _assemble_context
-> _plan
-> _generate_response
-> _update_memory
```

其中 `_load_context` 会读取 Memory（学生记忆）和 RAG（检索增强生成）资料，`_diagnose` 会执行 KT（知识追踪）诊断。因此现在的工具挂载更接近“执行完成后的观察记录”，还没有真正控制工具是否执行。

当前只有三个意图：

```text
answer_submission：提交答案
next_step_advice：询问下一步
general_chat：其他聊天
```

这会把概念问题、解题思路、当前步骤卡住、错因解释、推荐解释和闲聊都放进 `general_chat`，无法生成准确的工具计划。

## 3. 目标结构

目标调用链分成四层：

```text
第一层：Intent Router（意图路由器）
判断这次请求属于什么事情。

第二层：Tool Policy（工具策略）
根据意图和权限，确定允许、跳过和禁止的工具。

第三层：Execution Plan（执行计划）
确定节点依赖、并行关系、失败分支和状态写入顺序。

第四层：Plan Runner（计划执行器）
执行计划，收集结果，组装回复，并保存 TeachingTrace（教学追踪）。
```

完整流程：

```text
LearningEvent（学习事件）
-> Intent Router（意图路由器）
-> Policy Guard（策略检查）
-> Execution Plan Builder（执行计划生成器）
-> Plan Runner（计划执行器）
-> Context Assembler（上下文组装器）
-> Response Generator（回复生成器）或 State Writer（状态写入器）
-> TeachingTrace（教学追踪）
```

核心原则：

```text
明确的页面事件由规则决定；
模糊的聊天语义才交给 LLM；
先过滤工具，再让模型从少量候选工具中选择；
证据读取可以并行；
决策和状态写入必须串行；
LLM 只能建议路线，不能直接修改学习事实。
```

## 4. 意图设计

### 4.1 第一版意图清单

| 意图值 | 中文含义 | 典型输入 |
|---|---|---|
| `answer_submission` | 提交答案 | 点击提交按钮 |
| `next_question_action` | 点击下一题 | 点击下一题按钮 |
| `concept_question` | 询问数学概念 | “什么是一次函数？” |
| `solution_approach_question` | 询问整道题的解题思路 | “这道题从哪里入手？” |
| `stuck_on_current_problem` | 当前步骤卡住 | “我列出方程后不会变形了。” |
| `mistake_explanation` | 询问刚才为什么错 | “我的思路错在哪里？” |
| `next_step_request` | 询问下一步练什么 | “接下来推荐什么题？” |
| `recommendation_explanation` | 询问为什么推荐当前题 | “为什么给我推荐这道题？” |
| `review_summary` | 学习总结或复盘 | “总结一下我今天的学习。” |
| `off_topic_chat` | 无关闲聊 | “讲个笑话。” |

`clarification_needed`（需要澄清）只作为内部路由结果，不作为长期业务意图。它表示当前信息不足，需要先追问学生。

### 4.2 容易混淆的四类意图

```text
问知识本身
-> concept_question（概念问题）

问整道题应该怎么分析
-> solution_approach_question（解题思路问题）

已经做到某一步但无法继续
-> stuck_on_current_problem（当前步骤卡住）

已经正式提交答案，询问为什么判错
-> mistake_explanation（错因解释）
```

例如：

| 学生输入 | 当前状态 | 路由结果 |
|---|---|---|
| “什么是通分？” | 是否有当前题都不影响 | `concept_question` |
| “这道题先做什么？” | 有当前题 | `solution_approach_question` |
| “我通分以后不知道下一步了。” | 有当前题和已有步骤 | `stuck_on_current_problem` |
| “刚才为什么判错？” | 有最近一次正式判题 | `mistake_explanation` |

### 4.3 判断优先级

路由顺序固定为：

```text
1. 页面事件
2. 明确规则
3. LLM 结构化分类
4. 低置信度追问
```

页面事件优先级最高：

```text
answer_submitted -> answer_submission
next_question_requested -> next_question_action
hint_requested -> stuck_on_current_problem
review_summary_requested -> review_summary
```

这里的 `next_question_requested`（请求下一题）和 `review_summary_requested`（请求学习总结）是建议新增的后端业务事件，不是直接照搬前端按钮名称。

当前 `LearningEvent`（学习事件）已经有：

```text
answer_submitted：已经提交答案
question_recommended：已经产生题目推荐
hint_requested：已经请求提示
review_completed：已经完成复盘
```

其中 `question_recommended` 和 `review_completed` 表示事情已经完成，不能拿来表达“学生现在请求执行”。第一阶段需要扩展 `LearningEvent.type`，或者增加单独的动作接口，避免把请求事件和结果事件混为一谈。

聊天中出现“答案是 3/4”不能自动变成 `answer_submission`。只有提交按钮产生的正式事件才能写入作答事实。

### 4.4 路由输出

建议新增：

```python
class IntentResult(BaseModel):
    intent: RuntimeIntent
    confidence: float
    source: Literal["event_rule", "message_rule", "llm", "fallback"]
    reason: str
    needs_clarification: bool = False
    matched_rules: list[str] = Field(default_factory=list)
```

其中：

- `confidence`：判断把握，范围为 0 到 1。
- `source`：本次判断来自页面事件、消息规则、模型还是保守降级。
- `reason`：可审计原因，不是模型内部思考过程。
- `matched_rules`：命中的规则编号，便于测试和排错。

置信度建议：

```text
大于等于 0.80：采用该意图；
0.50 到 0.80：只允许读取轻量证据，不允许学习事实写入；
低于 0.50：不调用重工具，先追问学生。
```

## 5. 工具策略

### 5.1 工具分组

第一版把工具分为四组。

#### 只读事实工具

```text
load_task_state：读取当前题和作答状态
load_learning_state：读取 KT 学习状态
load_recent_history：读取近期作答与推荐历史
load_recommendation_evidence：读取已保存的推荐依据
question_bank_search：读取候选题
```

#### 教学证据工具

```text
rag_concept_search：检索概念资料
rag_question_search：检索当前题解析和相似题
memory_search：读取学生偏好、历史错因和有效策略
```

#### 决策工具

```text
recommend_questions：根据证据计算推荐排序
response_strategy：生成提示、讲解或复盘策略
```

决策工具可以产生建议，但不能直接修改掌握度。

#### 状态写入工具

```text
grade_answer：确定性判题
save_answer_event：保存正式作答事件
update_kt：更新 KT 学习事实
save_progress：保存学习进度
save_current_question：保存当前题
save_recommendation_evidence：保存推荐依据
memory_update：保存经过审核的学生记忆
persist_trace：保存 TeachingTrace
```

每个写入工具都必须声明具体能写什么，不能使用笼统的“允许写状态”。

### 5.2 各意图允许的工具

| 意图 | 必须调用 | 可选调用 | 禁止调用 |
|---|---|---|---|
| 提交答案 | 当前题、判题、保存答案、更新 KT、保存进度 | 无标准答案时跳过判题 | RAG、Memory、推荐器 |
| 点击下一题 | KT 状态、题库、历史、推荐器、保存当前题和推荐依据 | Memory | 作答写入 |
| 概念问题 | 概念 RAG | 知识点映射 | 更新 KT、推荐器、作答写入 |
| 解题思路 | 当前题、题目 RAG | Memory、只读 TeachingState | 更新 KT、作答写入 |
| 当前步骤卡住 | 当前题 | 题目 RAG、Memory、只读 TeachingState | 更新 KT、作答写入 |
| 错因解释 | 最近判题、当前题 | 题目 RAG、Memory、只读 KT 诊断 | 更新 KT、重新判题 |
| 下一步建议 | TeachingState、近期正式作答 | Memory | 推荐器、题库、选题后 RAG、作答写入、当前题写入 |
| 推荐解释 | 当前题、已保存的推荐依据 | 最近作答、Memory、只读 KT | 重新推荐、学习事实写入 |
| 学习复盘 | 学习进度、事件历史、Trace 历史 | Memory、KT 诊断 | 作答写入 |
| 无关闲聊 | 无 | 无 | KT、RAG、Memory、推荐器、状态写入 |

### 5.3 工具挂载结果

每个候选工具必须得到明确结果：

```text
mounted：允许并准备调用
skipped：本轮不需要
blocked：本轮禁止调用
```

建议结构：

```python
class ToolDecision(BaseModel):
    tool_id: str
    status: Literal["mounted", "skipped", "blocked"]
    reason_code: str
    reason: str
    state_write_scope: list[str] = Field(default_factory=list)
```

`reason_code` 使用稳定编码，例如：

```text
required_by_intent
optional_evidence
missing_current_question
missing_answer_record
forbidden_state_write
low_router_confidence
provider_unavailable
```

## 6. 执行计划

### 6.1 数据结构

```python
class PlanNode(BaseModel):
    node_id: str
    tool_id: str
    depends_on: list[str] = Field(default_factory=list)
    required: bool = True
    failure_policy: Literal["stop", "skip", "fallback"] = "stop"
    fallback_node_id: str | None = None


class ExecutionPlan(BaseModel):
    plan_id: str
    intent_result: IntentResult
    nodes: list[PlanNode]
    allowed_state_writes: list[str] = Field(default_factory=list)
```

`depends_on` 表示当前节点必须等待哪些节点完成。多个没有相互依赖的读取节点可以并行执行。

### 6.2 典型计划

#### 概念问题

```text
route_intent
-> policy_guard
-> rag_concept_search
-> assemble_context
-> generate_concept_response
-> persist_trace
```

#### 解题思路问题

```text
route_intent
-> policy_guard
-> 并行读取：
   load_task_state
   rag_question_search
   memory_search（可选）
-> assemble_context
-> generate_solution_approach
-> persist_trace
```

#### 当前步骤卡住

```text
route_intent
-> policy_guard
-> 并行读取：
   load_task_state
   rag_question_search
   memory_search（可选）
-> assemble_context
-> generate_step_hint
-> persist_trace
```

解题思路与当前步骤卡住可以使用相同工具，但回复策略不同：前者给整体方向，后者只解决当前卡点。

#### 提交答案

```text
load_current_question
-> grade_answer（有标准答案时）
-> save_answer_event
-> update_kt
-> compile_teaching_state
-> save_progress
-> persist_trace
```

这条链路保持串行和幂等，不进入 Agent 自由决策，不查 RAG，不查 Memory，不自动推荐下一题。

#### 点击下一题

```text
并行读取：
   load_learning_state
   load_question_bank
   load_recent_history
   memory_search（可选）
-> recommend_questions
-> select_next_question
-> save_current_question
-> save_recommendation_evidence
-> generate_short_reason
-> persist_trace
```

这里的 `recommend_questions` 不直接调用 SAFKT。候选题初筛后，先由
`CandidateKTScorer`（候选题知识追踪评分器）批量计算目标题概率，评分结果写入
selection context（选题上下文），推荐器只读取已经整理好的候选题事实和分数。

## 7. 失败与降级

失败处理不能只记录一个异常字符串。每个工具结果至少区分：

```text
healthy：正常
degraded：降级后仍可使用
unavailable：当前不可用
not_configured：没有配置
empty_result：调用成功但没有结果
invalid_input：输入不满足要求
blocked_by_policy：被策略禁止
```

关键降级规则：

```text
没有当前题
-> 不能生成当前题解题思路，先让学生选择或提供题目。

没有正式判题记录
-> 不能生成个性化错因结论，只能询问学生具体答案或提供通用检查方法。

没有推荐依据
-> 不能编造“根据你的薄弱点推荐”，只能说明当前证据不足。

RAG 为空
-> 可以使用模型基础数学能力生成保守解释，但不得伪造引用。

Memory 不可用
-> 使用默认讲解风格，不影响 KT 事实和主流程。

SAFKT 正常，但学生没有足够正式作答历史
-> 这是合法冷启动，可以基于基础题和内容完整度开始，不伪造薄弱点。

SAFKT 模型、映射或产物不可用
-> KT 相关选题请求停止并返回结构化错误，不能伪装成冷启动，也不能降级到 mock 或题库规则推荐。

低路由置信度
-> 不调用重工具，不写学习事实，先追问学生。
```

状态写入失败时，不允许继续假装成功。例如 `save_answer_event` 失败后，不能继续把这次答案当成已保存事实执行 `update_kt`。

## 8. TeachingTrace 记录

路由阶段至少记录：

```text
最终意图
判断来源
置信度
命中的规则
是否需要澄清
```

工具策略阶段至少记录：

```text
候选工具
mounted / skipped / blocked
每个决定的原因码
允许的状态写入范围
```

执行阶段每个节点至少记录：

```text
节点 ID
工具 ID
输入摘要
输出摘要
依赖节点
开始和结束时间
是否成功
是否降级
是否使用 fallback（备用方案）
证据引用
实际状态写入
```

禁止进入 Trace 的内容：

```text
模型内部思考过程
完整 Provider（外部服务商）原始响应
密钥和认证信息
Embedding（向量表示）
本地模型和 checkpoint（模型检查点）的私有路径
未经裁剪的学生隐私数据
```

## 9. 测试方案

测试分成四层。

### 9.1 路由单元测试

```text
页面事件是否始终覆盖聊天文本；
概念问题和解题思路是否能区分；
解题思路和当前步骤卡住是否能区分；
没有当前题时是否阻止当前题流程；
低置信度是否进入追问；
聊天里的答案是否不会变成正式提交。
```

### 9.2 工具选择测试

参考 BFCL（伯克利工具调用排行榜）的分类：

```text
应该调用一个工具；
应该调用多个工具；
应该并行调用多个工具；
不应该调用任何工具；
多个相似工具中选对一个；
工具参数缺失时阻止调用。
```

核心断言示例：

```text
concept_question 不挂载 update_kt；
off_topic_chat 不挂载任何重工具；
answer_submission 不挂载 RAG 和 Memory；
recommendation_explanation 不重新执行推荐器。
```

### 9.3 执行顺序测试

```text
save_answer_event 成功后才能 update_kt；
KT 诊断完成后才能个性化推荐；
选定题目后才能检索该题解析；
上下文组装完成后才能生成回复；
状态写入完成后才能保存最终 Trace。
```

### 9.4 最终状态测试

参考 `τ³-bench` 的做法，不只检查回复文字，还检查最终数据库状态：

```text
学生只问概念 -> mastery 不变化；
学生聊天里说答案 -> 不新增正式作答；
学生点击提交 -> 写入答案和 KT 状态，但不自动推荐；
学生问推荐原因 -> 推荐历史不新增；
学生重复提交同题同答案 -> 不重复更新 KT。
```

## 10. 分阶段开发顺序

### 第一阶段：扩展意图，不改变原执行流程

```text
扩展 RuntimeIntent；
增加 IntentResult；
实现页面事件规则和消息规则；
保留现有 MathTutorLearningLoop 作为兼容执行入口；
补齐路由单元测试。
```

### 第二阶段：让工具策略真正控制读取工具

```text
新增 ToolPolicy；
让概念问题、闲聊、提交答案不再全量读取 RAG / Memory / KT；
记录 mounted / skipped / blocked；
补齐工具选择测试。
```

### 第三阶段：迁移三个低风险只读场景

优先迁移：

```text
off_topic_chat
concept_question
solution_approach_question
```

这三类场景不写学习事实，适合先验证新的执行计划。

### 第四阶段：迁移推荐和错因解释

```text
next_step_request
recommendation_explanation
mistake_explanation
review_summary
```

重点验证推荐依据复用、KT 只读边界和证据不足降级。

### 第五阶段：迁移状态写入场景

最后迁移：

```text
answer_submission
next_question_action
```

这两条链路会修改学习状态，需要完成幂等、顺序和最终状态测试后再切换。

### 第六阶段：决定是否引入 LangGraph

如果自有 `ExecutionPlan + PlanRunner` 已经能够稳定表达节点、依赖、并行和失败分支，可以继续保留轻量实现。

只有出现下面需求时再引入 LangGraph（状态图编排框架）：

```text
长时间运行后恢复；
人工确认后继续；
复杂动态分支；
大量并行节点；
节点级 checkpoint（执行进度保存）。
```

## 11. 开源项目与论文取舍

### 建议吸收

- [LangGraph](https://github.com/langchain-ai/langgraph)：条件分支、并行节点、失败恢复和执行进度保存。
- [LlamaIndex](https://github.com/run-llama/llama_index)：根据结构化工具说明选择少量相关工具。
- [Semantic Kernel](https://github.com/microsoft/semantic-kernel)：工具白名单、调用前后过滤和权限控制。
- [Gorilla / BFCL](https://github.com/ShishirPatil/gorilla)：工具相关性、参数正确性和多轮工具调用评测。
- [τ³-bench](https://github.com/sierra-research/tau2-bench)：多轮对话中的业务规则和最终状态验证。

### 作为研究参考，不直接引入

- [ReAct](https://arxiv.org/abs/2210.03629)：吸收“行动、观察、再规划”，不采用无限自由调用。
- [Toolformer](https://arxiv.org/abs/2302.04761)：说明模型需要判断是否调用、何时调用和如何使用结果，当前阶段不训练专用模型。
- [Gorilla](https://arxiv.org/abs/2305.15334)：吸收工具检索和结构化参数思想，当前工具较少时不需要训练模型。
- [ToolLLM / ToolBench](https://arxiv.org/abs/2307.16789)：吸收“先缩小工具范围再规划”的思想，不采用面向一万多个工具的重型训练方案。
- [τ-bench](https://arxiv.org/abs/2406.12045)：吸收最终状态和多次运行可靠性评测，实际代码使用更新后的 `τ³-bench`。

## 12. 最终结论

第一版不追求一个可以自由调用所有工具的通用 Agent。

目标是建立一条受控链路：

```text
页面事件先确定强意图；
规则处理明确聊天；
LLM 只处理模糊分类；
工具策略缩小可用工具范围；
执行计划控制并行、顺序和失败；
状态写入由明确工具独占；
TeachingTrace 记录可审计过程；
测试同时检查工具调用和最终学习状态。
```

一句话概括：

```text
规则决定边界，模型辅助判断，计划控制执行，Trace 负责对账。
```
