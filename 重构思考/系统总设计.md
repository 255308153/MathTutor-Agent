# 系统总设计

这份文档记录 MathTutor Agent 的整体产品和系统结构构想。

它和另外几份文档的关系：

```text
系统总设计：页面长什么样、模块怎么分、状态怎么同步。
思考链路：一次事件进来后，系统怎么路由、调用工具、记录 trace。
记忆模块 / RAG模块：画像与知识资源各自怎么生产。
知识追踪模块：会不会怎么估、TeachingState 怎么编译、怎么和教学对账。
题目推荐与练习路径模块：先决定补弱、纠错、复习还是进阶，再选择下一题。
上下文总设计：本轮回答时系统看见什么、怎么组装与消费。
```

## 产品使用构想

页面的主心智模型是“当前题目 + 侧边 Agent 辅导”，不是纯聊天页面。

建议分成三个核心模块：

```text
1. 当前题目区
2. 左侧 Agent 对话模块
3. 下一题按钮 / 推荐说明
```

## 当前题目区

当前题目区负责展示学生现在正在做的题。

这里应该有：

```text
题干
答案输入
提交答案按钮
显示答案按钮
当前题状态
可选的简短推荐说明
```

提交答案不触发 Agent 对话，但会完成学习事实更新：

```text
学生写答案
-> 点击提交答案
-> 保存作答记录
-> 确定性判题（如题目内容完整）
-> 更新当前题状态
-> 更新 KT 并编译 TeachingState
-> 不触发 Agent 对话、RAG、Memory 或自动推荐
-> 不自动推荐下一题
```

也就是说，提交答案不是一次 Agent 对话；它会保存“学生做过这道题”、判题结果和更新后的学习状态。

显示答案按钮允许学生随时查看当前题的标准答案或参考解法：

```text
学生点击显示答案
-> 展开/展示当前题答案
-> 记录查看答案事件
-> 不触发 agent 对话
-> 不自动推荐下一题
-> 不改变学生已提交答案
```

如果学生还没有提交答案就查看答案，系统记录“查看过答案”这一学习事实，用于后续解释和推荐，但不直接改变 mastery，也不把它等同于一次作答。

## Agent 对话模块

左侧侧边栏是 Agent 对话模块。

它应该支持：

```text
新增对话
选择历史对话继续
围绕当前题提问
询问为什么推荐这道题
询问当前题怎么做
询问错因
询问下一步学习建议
```

Agent 对话模块会读取当前页面状态：

```text
当前题
当前题作答状态
学生历史作答
推荐题来源
系统内部学生画像/记忆
必要时的 RAG 资料
必要时的最新 TeachingState（教学状态快照）
```

但 Agent 不应该每次对话都调用所有工具。

它只在用户问题需要时调用：

```text
问当前题怎么做 -> task_state + 可选 RAG + 可选 Memory
问为什么推荐这题 -> recommendation_evidence + 可选 KT + 可选 Memory
问下一步做什么 -> TeachingState + 近期作答，只说明学习方向，不调用 Recommender
问泛化概念 -> 可选 RAG
闲聊 -> 不调用重工具
```

这里的 Memory 是内部系统能力，不是用户可直接操作的功能。

用户不能手动新增、删除、禁用或编辑记忆。

系统只在后台根据学习行为和对话证据维护学生画像，用来辅助个性化讲解和推荐。

## 下一题按钮

下一题按钮是一个明确的系统动作，不是普通聊天。

点击后：

```text
读取最新 TeachingState
读取历史做题记录
读取题库候选
可选读取 Memory
对初筛候选题批量计算 SAFKT 目标题概率
调用 Recommender 选下一题
更新当前题
保存 pending/current question 状态
生成简短推荐说明
```

这个按钮应该自动把页面跳到下一题。

同时在题目区的小位置展示一句简短说明：

```text
推荐原因：你刚才在分数通分上出错，这题会继续练同一知识点，但难度略低。
```

如果用户在 Agent 对话里追问“为什么选这道题”，Agent 再读取更完整的推荐证据，生成更详细解释。

## 换题按钮与反馈重排

题目区应该保留简洁心智：页面上仍然只展示一道当前推荐题。

但系统内部不应该只生成一道题，而应该维护一个候选题池：

```text
Recommender（推荐器）
-> 生成候选题池
-> 前端只展示第一道题
-> 学生可以点击换题
-> 记录 RecommendationFeedback（推荐反馈）
-> 根据反馈重排或重选候选题
-> 自动刷新当前题
```

也就是说，产品体验是“只推荐一道题”，系统能力是“可反馈、可调整、可追溯的推荐”。

换题按钮应该放在当前题目区，和下一题按钮区分开：

```text
下一题：学生接受当前学习推进，进入系统推荐的下一题。
换题：学生不接受当前推荐题，反馈原因后让系统调整推荐。
```

点击换题后弹出反馈框，而不是直接随机换题。

反馈框可以包含：

```text
太简单
太难
不想练这个知识点
题型不喜欢
已经做过类似题
想先复习概念
其他：自由输入
```

这些反馈会形成结构化的 `RecommendationFeedback`（推荐反馈）。

推荐调整规则：

```text
太难 -> 降低 difficulty（难度），优先选择同知识点基础题。
太简单 -> 提高 difficulty（难度），或切换到综合应用题。
不想练这个知识点 -> 在其他薄弱点中选题，但记录跳过原因。
题型不喜欢 -> 降低当前题型权重。
已经做过类似题 -> 提高近期重复惩罚。
想先复习概念 -> 先记录“先复习概念”的反馈，再按复习目标推荐新题。
自由输入 -> 由 Agent（智能体）抽取反馈意图，再交给推荐器调整。
```

反馈可以影响推荐排序、讲解策略和题型偏好，但不能直接改写 KT（Knowledge Tracing，知识追踪）的掌握度事实。

例如：

```text
学生说“太简单”
-> 说明当前推荐不符合体验
-> 可以提高推荐题难度
-> 不能直接写成“学生已经掌握该知识点”
```

换题过程也要写入长期学习记录和 TeachingTrace（教学追踪记录）。至少保留最近 10 条换题反馈：

```text
原推荐题
学生反馈
调整规则
新推荐题
推荐证据
是否来自同一候选题池
反馈时间
前后题目难度和知识点
```

每条换题反馈至少包含：

```text
原推荐题、换题原因、学生补充说明、新推荐题、调整规则、时间
```

这样后续追问“为什么换成这道题”时，Agent 可以解释清楚：

```text
因为你反馈上一题太难，所以系统保留同一个知识点，但换成了更基础的题。
```

## 状态同步原则

当前题目区、下一题按钮、Agent 对话模块共享同一份学习状态。

```text
提交答案 -> 更新作答状态
显示答案 -> 更新答案查看状态/记录查看事件
点击下一题 -> 更新 current_question
点击换题 -> 记录 RecommendationFeedback（推荐反馈），重排候选题，刷新 current_question
Agent 对话 -> 读取当前状态，并在必要时由系统后台更新内部画像
历史对话 -> 可以继续读取当时或当前的题目上下文
```

这里要区分两类状态：

```text
学习事实状态：题目、学生答案、标准答案、答案查看状态、判题结果、进度、当前题
对话状态：某个 Agent 对话里问过什么、解释过什么
内部画像状态：系统从长期学习行为中提取的偏好、错因、有效策略
```

学习事实状态是全局共享的。

对话状态属于某个 conversation，但可以引用当前学习事实。

内部画像状态由系统维护，不提供给用户直接操作。

## 设计边界

```text
题目区负责做题和保存作答状态。
显示答案按钮负责让学生随时查看当前题答案。
下一题按钮负责推进当前题。
换题按钮负责收集推荐反馈并调整当前推荐题。
Agent 侧边栏负责解释、答疑、复盘和学习建议。
提交答案不触发 Agent，但会完成判题、学习事实保存、KT 更新和 TeachingState 编译。
显示答案不触发 Agent。
换题反馈只进入结构化换题流程，不变成自由聊天。
Agent 需要基于当前题和历史状态回答问题。
记忆系统是内部能力，用户不直接操作。
```

一句话总结：

```text
题目是主界面，Agent 是侧边辅导层，下一题按钮是明确的学习推进动作。
```
