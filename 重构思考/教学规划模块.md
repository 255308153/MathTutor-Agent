# 回复与教学策略设计

这份文档总结 MathTutor Agent 在学生主动提问后，应该怎样读取证据并生成对应回复。

它关注的不是“下一题选哪一道”，而是：

```text
学生现在问的是什么？
系统需要读取哪些事实和资料，才能给出对应回复？
```

---

## 1. 模块一句话定义

```text
回复流程读取学习事实、诊断结果、知识证据和相关记忆，
根据学生主动提出的问题生成对应回复，并记录回复依据。
```

这里不设置一个主动安排教学的独立规划模块。学生没有提问时，Agent 不主动决定讲什么。

例如：

```text
这题做错了 -> 先处理错因，再给相近题巩固。
学生说太难 -> 降低难度，换一道同知识点基础题。
学生问为什么推荐 -> 解释推荐依据，而不是重新规划掌握度。
学生卡在步骤里 -> 给分步提示，而不是直接换题。
```

---

## 2. 和其他模块的关系

回复流程不直接生产学习事实，也不直接维护题库或选择下一题。

它位于这些模块之后：

```text
KT / DGEKT（Knowledge Tracing，知识追踪模型）
-> TeachingState（教学状态）
-> RAG（Retrieval-Augmented Generation，检索增强生成）
-> Memory（记忆模块）
-> Recommender（仅在需要下一题时）
-> 回复生成
```

各模块职责：

```text
KT / DGEKT（知识追踪模型）：判断掌握度、薄弱点、遗忘风险和预测答对概率。
TeachingState（教学状态）：把学习事实整理成后续模块可读的状态。
RAG（检索增强生成）：提供题目解析、概念解释、错因模式和学习策略证据。
Memory（记忆模块）：提供学生长期偏好、常见错因和有效学习策略。
Recommender（推荐器）：根据目标和约束筛选、排序候选题。
回复流程：根据学生当前问题读取必要证据并生成自然语言回复。
TeachingTrace（教学追踪记录）：记录学生输入、AI 完整回复、使用证据和状态变化。
```

一句话：

```text
推荐器负责“下一题选什么”；
回复流程负责“学生问什么，就基于证据回答什么”。
```

---

## 3. 输入

教学规划模块应该读取治理后的上下文，而不是直接读取外部 provider 的原始数据。

核心输入包括：

```text
intent（用户意图）
learning_event（学习事件）
KT diagnosis（知识追踪诊断）
TeachingState（教学状态）
rag_context（RAG 检索证据）
student_memory（学生记忆）
recommended_questions（推荐候选题）
RecommendationFeedback（推荐反馈）
assembled_context（组装后的上下文包）
```

其中：

```text
intent（用户意图）：例如提交答案、询问下一步、请求提示、要求换题。
learning_event（学习事件）：例如作答、查看答案、点击下一题、点击换题。
KT diagnosis（知识追踪诊断）：薄弱知识点、遗忘风险、预测答对概率等。
rag_context（RAG 检索证据）：概念、题解、错因、策略等知识资源。
student_memory（学生记忆）：学习偏好、历史错因、有效策略等。
recommended_questions（推荐候选题）：推荐器给出的候选题池。
RecommendationFeedback（推荐反馈）：学生对当前推荐题的反馈。
assembled_context（组装后的上下文包）：经过裁剪、脱敏和证据治理后的上下文。
```

---

## 4. 输出

回复流程可以在内部生成一份轻量的回复说明，但它不是独立的教学计划，也不会主动安排后续教学。

第一版可以包含：

```text
intent（学生当前问题类型）
response_type（回复类型）
mistake_diagnosis（错因诊断）
evidence（证据）
trace_refs（追踪引用）
```

示例：

```text
intent: mistake_explanation（学生询问错因）
response_type: worked_example_steps（分步说明）
mistake_diagnosis: 分母直接相加，没有先通分
evidence: 判题结果、KT 诊断、RAG 错因资料
```

## 5. 教学动作类型

教学规划模块至少需要支持这些动作。

### 5.1 概念解释

适用场景：

```text
学生问概念是什么。
学生对基础定义不清楚。
RAG 有对应 concept_note（概念笔记）。
```

动作：

```text
先解释概念含义。
再给一个小检查问题。
必要时让学生用自己的话复述。
```

### 5.2 分步提示

适用场景：

```text
学生卡在当前题。
学生说“不会做”“下一步是什么”。
当前题有解析或步骤证据。
```

动作：

```text
不直接给完整答案。
先定位当前步骤。
给最小提示。
必要时逐步展开。
```

### 5.3 错因处理

适用场景：

```text
学生提交错误答案。
系统有 deterministic grading（确定性判题）结果。
RAG 或题库里有 mistake_pattern（错因模式）。
```

动作：

```text
指出错在什么知识点或步骤。
避免说“粗心”“不认真”等无证据心理判断。
给一题相近或稍低难度题巩固。
```

### 5.4 巩固掌握

适用场景：

```text
学生刚做对。
但 KT（知识追踪）认为该知识点还不够稳定。
```

动作：

```text
保留刚才有效解法。
推荐相近难度题。
观察是否能稳定迁移。
```

### 5.5 快速复习

适用场景：

```text
遗忘风险高。
学生偏好短复习。
当前知识点适合记忆型练习。
```

动作：

```text
先快速回忆事实或规则。
再用短题即时检查。
```

### 5.6 挑战反思

适用场景：

```text
学生基础掌握较稳。
推荐器给出较高难度或综合题。
```

动作：

```text
给稍有挑战的应用题。
要求学生说明建模思路或解题策略。
```

## 6. 单题展示与候选题池

产品界面上应该只展示一道当前推荐题。

这样学生不会因为选择太多而分心。

但系统内部不应该只生成一道题。

推荐链路应该是：

```text
Recommender（推荐器）
-> 生成候选题池
-> 前端只展示一道题
-> 其余候选题保留为可调整空间
```

一句话：

```text
前端是单题体验，后端是多候选题池。
```

这样既能保持学习节奏，又能支持换题和反馈调整。

---

## 7. 换题按钮与推荐反馈

当前题目区应该有换题按钮。

换题不是随机换一题，而是一次结构化反馈动作。

点击换题后弹出反馈框：

```text
太简单
太难
不想练这个知识点
题型不喜欢
已经做过类似题
想先复习概念
其他：自由输入
```

提交后形成 `RecommendationFeedback`（推荐反馈）。

推荐反馈进入结构化换题流程，由练习路径规则和推荐器决定下一步：

```text
太难 -> 降低 difficulty（难度），优先换同知识点基础题。
太简单 -> 提高 difficulty（难度），或换综合应用题。
不想练这个知识点 -> 在其他薄弱点中选题，但记录跳过原因。
题型不喜欢 -> 降低当前题型权重。
已经做过类似题 -> 提高近期重复惩罚。
想先复习概念 -> 先生成概念复习动作，再推荐新题。
自由输入 -> Agent（智能体）抽取反馈意图，再交给推荐器调整。
```

页面行为：

```text
学生点击换题
-> 弹出反馈框
-> 学生提交反馈
-> 结构化反馈分类
-> Recommender（推荐器）重排或重选题
-> 自动刷新当前题
-> 写入 TeachingTrace（教学追踪记录）
```

---

## 8. 和 KT 模型的边界

换题反馈不应该直接影响 KT（Knowledge Tracing，知识追踪模型）。

原因：

```text
学生说“太难”，只能说明当前推荐体验不合适。
学生说“太简单”，不能直接证明学生已经掌握。
学生说“不想练这个知识点”，这是当前意愿，不是掌握度证据。
```

正确边界：

```text
作答结果 -> 可以影响 KT（知识追踪）。
换题反馈 -> 不直接影响 KT，只影响推荐和教学策略。
```

间接影响路径：

```text
换题反馈
-> 调整推荐题
-> 学生作答新题
-> 新题作答结果
-> KT（知识追踪）更新学习事实
```

反馈可以进入：

```text
Recommender（推荐器）
练习路径规则
Memory（记忆模块）
TeachingTrace（教学追踪记录）
```

反馈不能直接写入：

```text
mastery（掌握度）
weak_concepts（薄弱知识点）
forgetting_risk（遗忘风险）
prediction_probability（预测答对概率）
```

一句话：

```text
反馈可以改变“下一题给什么、怎么讲”，但不能直接改变“学生会不会”。
```

## 9. Trace 与可解释性

每次回复和推荐都应该写入 TeachingTrace（教学追踪记录）。

普通回复至少记录：

```text
本轮 intent（用户意图）
当前题
判题结果
KT 诊断摘要
RAG 证据
Memory 证据
候选题数量
选中的教学动作
推荐原因
证据缺口
```

换题过程额外记录：

```text
原推荐题
学生反馈
反馈解释
调整规则
新推荐题
新推荐证据
是否来自同一候选题池
是否触发重新检索或重新推荐
```

这样学生追问时，Agent（智能体）可以回答：

```text
因为你反馈上一题太难，所以系统保留同一个知识点，
但换成了更基础的题，并继续观察你后续作答。
```

## 10. 第一版实现建议

第一版不要做过重。

可以先实现这些能力：

```text
1. 按学生问题类型读取必要证据并生成回复。
2. Recommender（推荐器）返回候选题池，而不是只返回单题。
3. 前端只展示候选题池第一题。
4. 增加换题按钮和反馈弹窗。
5. 增加 RecommendationFeedback（推荐反馈）事件。
6. 根据反馈做规则化重排，并至少保留最近 10 条换题反馈。
7. 换题过程写入 TeachingTrace（教学追踪记录）。
8. 保证反馈不直接改写 KT（知识追踪）事实。
```

第一版规则可以是确定性的，不必急着让 LLM（Large Language Model，大语言模型）参与所有判断。

LLM 更适合处理：

```text
自由输入反馈的意图抽取。
根据治理后的证据生成自然语言回复。
把换题原因解释给学生。
```

不适合直接处理：

```text
掌握度更新。
学习事实写入。
题库 canonical mapping（标准映射）修改。
```

## 11. 本阶段结论

回复流程的核心不是主动安排学生下一步，而是在学生提问后有依据地回答：

```text
读事实
看证据
按问题生成回复
可反馈
可调整
可追溯
不越权写 KT
```

产品上保持简单：

```text
学生只看到一道当前推荐题。
学生可以点击换题并说明原因。
系统根据反馈自动换题并刷新页面。
```

系统上保持稳健：

```text
推荐器维护候选题池。
回复流程只响应学生主动提出的问题。
KT 只接收真实作答证据。
TeachingTrace 记录每一步为什么这么做。
```
