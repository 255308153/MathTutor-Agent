# 思考链路

这份文档记录 MathTutor Agent 后续重构时的“思考链路”设计。

这里的“思考链”不是暴露 LLM 的内心推理，而是记录系统怎样判断学生意图、怎样按需调用工具、怎样组装证据、怎样生成回复，并把过程写入 TeachingTrace。

上下文「装什么、怎么裁、给谁用」见 `上下文总设计.md`；本文侧重路由与工具调用顺序。

## 一句话目标

当前系统不应该每次对话都固定调用 RAG 和 KT。

更合理的方式是：

```text
学生输入
-> 意图识别
-> 判断本轮需要哪些工具
-> 按场景调用工具
-> 组装证据
-> 按学生问题生成回复，或在明确请求时推荐题目
-> 生成回复
-> 记录 TeachingTrace
```

也就是：先路由，再按需调用工具。

## 总体调用链

```text
Observe：观察学生输入、当前题、学习状态
Route：判断意图和工具策略
Retrieve：按需查题库、RAG、Memory、历史记录
Diagnose：按需调用 KT/DGEKT
Assemble：组装本轮上下文和证据
Respond / Recommend：生成回复，或在明确请求时推荐题目
Act：生成回复、更新状态/记忆
Trace：记录工具调用、证据、决策和边界
```

核心原则：

```text
证据收集可以并行。
决策和状态写入必须串行。
```

## 意图类型

### 1. 无关闲聊

例子：

```text
你是谁？
讲个笑话。
我有点累。
今天天气怎么样？
```

处理方式：

```text
不调用 KT
不调用 RAG
不更新学习状态
轻量回复，必要时把学生拉回学习任务
```

Trace 记录：

```text
intent = off_topic_chat
tool_calls = []
state_write = none
```

### 2. 泛化数学问题

例子：

```text
分数加法怎么做？
什么是一次函数？
为什么移项要变号？
```

处理方式：

```text
可选调用 RAG
不调用 KT
不更新 mastery
生成概念解释或例子
```

如果问题没有绑定当前题，就不要把它当成学习事实。

### 3. 当前题卡住

例子：

```text
这道题我不会。
卡在第二步了。
为什么这里要通分？
给我一点提示。
```

处理方式：

```text
读取当前 task_state
可选调用 RAG 查题目解析、概念解释、错因模式
可选调用 Memory 查历史错因和偏好
根据学生当前问题，直接生成提示、步骤说明或概念解释
通常不调用 KT；如果已有最新 TeachingState，只读取，不重新计算
不更新 mastery
```

只有后续学生明确问“为什么错 / 下一步做什么 / 总结一下”时，才触发 agent 决策。

### 4. 提交答案

例子：

```text
学生在答案输入框填写 3/4，并点击提交按钮。
聊天中提到“答案是 3/4”不自动形成正式作答事件。
```

处理方式：

```text
不触发 Agent 对话
不调用 RAG、Memory 或 Recommender
先做确定性判题（如题目内容完整）
保存作答事实
更新 KT 并编译 TeachingState
返回保存结果或简单确认
```

这是状态保存流程，不是教学决策流程。

如果需要基于这次提交做诊断、推荐或讲解，应由后续请求触发：

```text
学生问“我错在哪？” -> stuck_on_current_problem / mistake_explanation
学生问“下一步练什么？” -> next_step_request
学生问“总结一下” -> review_summary
```

### 5. 问下一步做什么

例子：

```text
我下一步练什么？
我还有什么薄弱点？
```

处理方式：

```text
读取最新 TeachingState
可选调用 Memory
读取近期正式作答
生成学习方向建议
```

这一步不读取候选题、不调用 Recommender、不修改当前题。学生点击“下一题”后，
系统才进入选题流程；询问推荐原因时读取已经保存的推荐证据。

### 6. 问为什么推荐这道题

例子：

```text
为什么推荐这道题？
这题和我刚才做的有什么关系？
为什么不让我做难一点的？
```

处理方式：

```text
读取当前推荐记录
读取推荐时保存的 evidence
可选读取 KT/DGEKT 诊断摘要
可选读取最近作答记录
可选读取 Memory
生成推荐解释
```

这类问题通常不需要重新推荐，也不需要重新写学习状态。

重点是解释“当时为什么选它”。

### 7. 学习总结 / 复盘

例子：

```text
总结一下我今天学得怎么样。
我哪里容易错？
最近有什么进步？
```

处理方式：

```text
读取学习进度
读取 recent events / trace history
读取 Memory
可选调用 KT 诊断当前状态
生成复盘
```

RAG 通常不需要，除非复盘里要补概念解释。

## 哪些判断写死，哪些交给 LLM

不要全部写死，也不要全部交给 LLM。

推荐策略：

```text
规则优先
LLM 辅助
Policy guard 兜底
```

### 写死的判断

这些不要让 LLM 猜：

```text
点了提交按钮 -> answer_submission
点了推荐下一题 -> next_step_request
点击下一题按钮 -> next_question_action
当前有 current_question 且学生说“不会/提示/卡住” -> stuck_on_current_problem
当前有推荐题且学生问“为什么推荐” -> recommendation_explanation
明确说“总结/复盘/我学得怎么样” -> review_summary
```

这些判断和状态写入强相关，误判会影响 KT 和学习记录。

### 交给 LLM 的判断

这些语义比较模糊，可以让 LLM 分类：

```text
“这里为什么这样？”
“我有点不懂。”
“我该继续练还是复习？”
“这个和刚才那个有什么区别？”
```

LLM 只输出结构化建议，不直接写状态：

```json
{
  "intent": "stuck_on_current_problem",
  "confidence": 0.82,
  "needs_tools": ["task_state", "rag_search", "memory_search"],
  "state_write": false,
  "reason": "学生在当前题上下文中请求提示"
}
```

### Policy guard

LLM 判断后还要过安全检查：

```text
提交答案事件本身不触发 agent 决策
没有提交答案记录 -> 不基于作答事实更新学习状态
没有 current_question -> 不能走当前题卡住流程
没有 recommendation evidence -> 不能解释为个性化推荐，只能给通用说明
SAFKT 正常但没有学习历史 -> 使用冷启动学习方向，不伪造薄弱点
置信度太低 -> 不写状态、不调用重工具，给出保守回复
RAG 结果为空 -> 记录 evidence gap，不伪造引用
Memory 是内部能力，用户不直接操作
内部画像无可用证据 -> 不纳入上下文
```

一句话：

```text
LLM 提议路线，规则决定能不能走。
```

## 可以并行的调用

### 当前题卡住

可以并行：

```text
load_task_state
rag_search
memory_search
```

然后串行：

```text
assemble_context
-> generate_response
```

### 问下一步做什么

可以并行：

```text
load_teaching_state
memory_search
load_recent_history
```

然后串行：

```text
generate_next_step_direction
-> persist_trace
-> generate_response
```

这里 RAG 可以放在推荐之后，因为没选题前不知道要查哪道题的解释。

### 点击下一题按钮

点击下一题按钮是明确动作，可以直接走推荐链路，不需要 LLM 判断意图。

可以并行：

```text
kt_diagnose
memory_search
load_question_bank
load_recent_history
```

然后串行：

```text
recommend_questions
-> select_next_question
-> save_current_question
-> save_recommendation_evidence
-> generate_short_recommendation_reason
-> update_page_current_question
```

这里生成的是页面上的简短说明，不是完整 Agent 对话。

### 解释为什么推荐当前题

可以并行：

```text
load_current_question
load_recommendation_evidence
load_recent_answer_events
memory_search
```

可选：

```text
kt_diagnose
```

然后串行：

```text
assemble_context
-> generate_recommendation_explanation
-> append_agent_message
```

### 提交答案

提交答案不触发 Agent 对话，但会完成判题、学习事实保存、KT 更新和 TeachingState 编译。

```text
answer_submission
-> load_current_question
-> save_answer_event
-> optional_deterministic_grading
-> persist_progress_snapshot
-> record_state_trace
```

这条链路应该保持简单、串行、可幂等。

```text
同一题同一答案重复提交 -> 不重复写入学习事实
没有标准答案 -> 只保存未判题状态
有标准答案 -> 保存判题结果
```

后续如果学生问问题，再由新的 intent 触发 agent：

```text
answer_submission 已保存
-> 学生问“为什么错”
-> 读取保存的答题状态
-> 再调用 RAG / 内部画像并生成回复
```

### 学习总结 / 复盘

可以并行：

```text
load_progress
load_recent_events
load_trace_history
memory_search
kt_diagnose
```

然后串行：

```text
summarize_evidence
-> generate_review_response
```

## 必须串行的地方

这些不能随便并行：

```text
intent_router -> tool_policy
answer_submission -> save_answer_event -> persist_progress_snapshot
kt_diagnose -> recommend_questions
recommend_questions -> rag_for_selected_question
retrieve_evidence -> assemble_context
assemble_context -> generate_response
state_write -> final_trace_save
```

原因：

```text
提交答案只更新学习事实、判题结果和 KT，不直接触发 Agent 对话。
需要先有已保存的作答事实，后续请求才能基于它诊断或讲解。
没有 KT 结果，不能做个性化推荐。
没有证据结果，只能生成明确标注证据不足的保守回复。
会影响学习事实的状态写入必须有顺序。
```

## LangGraph / DAG 设计

这条链路很适合用 LangGraph 或类似 DAG/状态机实现。

推荐结构：

```text
START
-> route_intent
-> policy_guard
-> conditional edge
   -> off_topic_chat
   -> general_math_question
   -> stuck_on_current_problem
   -> answer_submission
   -> next_step_request
   -> next_question_action
   -> recommendation_explanation
   -> review_summary
-> generate_response
-> record_trace
-> END
```

### 子图：off_topic_chat

```text
off_topic_chat
-> generate_light_response
-> record_no_tool_trace
```

### 子图：general_math_question

```text
general_math_question
-> maybe_rag_search
-> generate_concept_explanation
-> record_trace
```

### 子图：stuck_on_current_problem

```text
stuck_on_current_problem
-> 并行：
   -> load_task_state
   -> rag_search
   -> memory_search
-> assemble_context
-> generate_response
-> record_trace
```

### 子图：answer_submission

```text
answer_submission
-> load_current_question
-> deterministic_grading_if_possible
-> save_answer_event
-> update_kt
-> compile_teaching_state
-> persist_progress
-> record_state_trace
```

注意：

```text
answer_submission 子图不进入 agent 决策。
不查 RAG。
不查 Memory。
不推荐下一题。
不生成讲解。
它只是把学生作答保存成后续 agent 可以读取的状态。
```

### 子图：next_step_request

```text
   -> diagnose_kt
```

```text
-> save_current_question
```

### 子图：recommendation_explanation


## TeachingTrace 应该记录什么

每个工具节点和每轮回复都应该记录：

```text
为什么调用
输入摘要
输出摘要
是否成功
是否降级
是否使用 fallback
是否写状态
证据边界
这个结果如何影响下一步
学生输入
AI 完整回复
回复使用的证据和引用
后续是否产生作答、换题或反馈结果
```

示例：

```json
{
  "stage": "rag_search",
  "actor": "rag",
  "content": "为当前卡住题检索题目解析和错因模式。",
  "metadata": {
    "reason": "学生请求当前题提示",
    "input_summary": {
      "question_id": "q_frac_001",
      "concept_id": "c_fraction_addition"
    },
    "output_summary": {
      "result_count": 2,
      "doc_types": ["question_explanation", "mistake_pattern"]
    },
    "state_write": false,
    "boundary": "RAG 只提供解释，不覆盖 KT facts"
  }
}
```

## 最终原则

```text
不是每句话都调用重工具。
不是每次都查 RAG。
不是每次都调 KT。
不是 LLM 想调什么就调什么。
```

最终应该是：

```text
规则判断明确事件。
LLM 判断模糊语义。
Policy guard 防止错误写状态。
DAG/LangGraph 编排调用链。
工具节点收集证据。
回复流程根据学生主动提出的问题生成回答。
TeachingTrace 记录全过程。
```

一句话总结：

```text
用 DAG 管流程，用规则管安全，用 LLM 管模糊判断，用 TeachingTrace 管可解释性。
```
